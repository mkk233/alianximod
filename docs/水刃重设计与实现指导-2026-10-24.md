## 2. 玩法节奏与参数

### 2.1 沿用的基准

撰写时登记在 [WaterTechniques.java](../src/main/java/com/bslx/XueXiMod/shu/WaterTechniques.java) 第 20–22 行：伤害 7、冷却 14、复杂度 0、直线寿命 10、速度 1.3、厚度 0.35、`along(3.2)`、`span(0.7)`、`energy(1.35)`、`wetness(6)`。当时第 35 行类型写的是 `MAGIC`。这是审计基线，不是本轮结束后的源码快照。数值本身仍是伤害 7、冷却 14、魔力 14、湿润 6、复杂 0。

魔力没有单独 override。[Technique.java](../src/main/java/com/bslx/XueXiMod/shu/Technique.java) `manaCost()` 对普通攻击是 `ceil(基础伤害 × 2)`，7 点伤害即 14。保持这个公式，不要另写魔耗。

基础法杖在 [ModItems.java](../src/main/java/com/bslx/XueXiMod/item/ModItems.java) 里冷却减免 0.10。[SkillSegmentMath.java](../src/main/java/com/bslx/XueXiMod/network/SkillSegmentMath.java) `scaleCooldown` 做 `round(tick × 0.9)`，14 tick 会变成 13。[SkillUsePacket.java](../src/main/java/com/bslx/XueXiMod/network/SkillUsePacket.java) 只有法杖分支才读这项减免。改成剑技后水刃走非杖分支，减免保持 0，基础冷却仍是 14。不要为水刃再乘 0.9。

`energy(1.35)` 今天是几何系数，不是伤害倍率。下文半径 2.4、半宽 0.16 是未缩放建议基准。最终 scale 只在组快照准备入口汇合一次：定义上的 1.35、公共链聚能、附魔半径倍率。若沿用 `CastFrame` 里已经合并好的 scale，就直接用那一个数，不要再乘 1.35 或链上倍率。快照里的半径和半宽已是最终尺寸，[TechniqueHitSpec.java](../src/main/java/com/bslx/XueXiMod/shu/technique/release/entity/TechniqueHitSpec.java) 不得再放大。不增加伤害，不增加命中次数。

直线速度 1.3 和盒体尺寸停止作为水刃的命中体。它们不代表弧带已经存在。

### 2.2 三拍

拍序固定。第 0 拍左斜斩，第 1 拍右斜斩，第 2 拍横斩，然后回到左斜。

建议角度（待实测，相对冻结瞄准，扫角从起手到收势）：

| 拍 | 斩面滚转 | 扫角 | 读感 |
| --- | --- | --- | --- |
| 0 左斜 | +40° | -50° → +40° | 起势短，弧顶偏上 |
| 1 右斜 | -40° | +50° → -40° | 与左斜镜像衔接 |
| 2 横斩 | 0° | -70° → +70° | 弧顶在眼前高度，尾部收薄 |

半径建议 2.4 格，半宽建议 0.16 格。二者都是未缩放基准，实际尺寸只经过 2.1 的那一次 scale。

一按只提交一组水刃。这一次释放的费用和冷却独立于上一拍。潮湿仍按该宿主的命中走现有结算。双重计划里的多个水刃宿主不在这里各开一套冷却，见 6.1。上一组还在播余流时，只要这一次释放的冷却已好，可以再按出下一拍；两段弧可以同时存在，后一段不拖动前一段。

### 2.3 拍号不变量

拍号和 [ChainProgress.java](../src/main/java/com/bslx/XueXiMod/network/ChainProgress.java) 的链游标分开存。链游标仍只管装配链从哪一段开始。水刃拍号不写入 `xueximod_chain_step`。

推进条件只有一条：该水刃宿主组真实 `notifyCommit` 成功。`HostBeatHooks.beforeCopies`、按键、预定 schedule、复制实体个数都不推进。拍钟和动作开始用 `Level.getGameTime()`，不用回执上的服务端 tick。

| 情形 | 结果 |
| --- | --- |
| 普通一斩 | 该组一次 |
| 一分为三的同一宿主组 | 三份共享拍号，只一次 |
| 双重释放里的独立水刃宿主 | 按实际提交次序，每个成功宿主一次。正常双重是 A 当刻、B 在 +5 tick，不在 A 提交时提前推进 B |
| 同一 tick 的并行不同组 | 只用稳定序号消除歧义：接触时间，再稳定目标 id，再宿主序号。这不用于把未来的 B 提前记入 |
| 动作碰撞打出的多组独立水刃 | 每组在自己的提交时刻推进一次 |
| 同一 `groupId` 的重复回调 | 返回已有快照和结果，不再生成，也不再推进 |
| 父动作自己的冷却 | 不变。动作加双重时，父动作的四术式冷却仍只合计一次；没有碰撞时只有动作冷却 |
| 首次整链预检失败、冷却中重按 | 不扣费、不进冷却、不推进、不刷新窗口 |
| 已接受之后的复核失败 | 该成员不推进、不刷新窗口。不回滚已成功前段，父会话冷却和链游标按公共失败政策保留 |

窗口从成功 `commitGroup` 的 `gameTime` 起算。只有间隔大于 40 tick 才从第 0 拍打；间隔恰好 40 tick 仍衔接。冷却中连按不把窗口续上。

双重的时序、费用和冷却沿 [双重释放调整意见与实现指导-2026-10-23.md](双重释放调整意见与实现指导-2026-10-23.md)，本文不改那套设计。动作加双重仍是碰撞当刻出 A、5 tick 后出 B；多次碰撞各自开组。

存储键：玩家 UUID + 技能槽。载体不是物品注册名。服务端每个玩家 tick，以及准备和激活当时，立刻观察主手 `ItemStack` 的引用、当前选中的背包槽和代数。引用或选中槽变了，代数加一，并清掉该玩家的三拍连续状态。同一把栈上的耐久或 NBT 原地变化不重置。同型号的新栈会重置。换到别的槽再选回来，经过观察之后也重置，不接旧窗口。同一个 tick 里先换走又完全换回、中间没有观察，轮询仍看见原来的引用，不会记成变化；这里只保证已经观察到的变化。不写 NBT。另一次技能槽请求不会改写已经交给会话或动作计划的父 `CastSource`。死亡、离线、换维和停服清掉身份和拍号。

法杖上的旧水刃永远通不过持剑预检，所以成功拍号不会记在法杖 NBT 上。

## 3. 视觉与像素画

### 3.1 画面

水带是一条有限弧，不是闭合环。带芯青蓝，浪缘更浅更窄，弧顶最亮，两端变薄。白沫和水滴只挂在弧顶外缘和断水尾，量少。主动区间内水带随扫角长出；扫到年龄 6 并补完末段后不再产生新的伤害扫掠，只留断开的余流变淡，直到第 10 tick。

角色挥剑和这道弧共用同一次冻结平面和同一进度。人走开以后，剑跟着人，弧留在提交时的世界坐标。这是取舍。

落点、交错、动作接触把弧放在远端时，远端弧仍是「挥剑驱动的水弧」，不要求水体贴住某把实体剑。

## 5. 实现方案

下列带「拟新增」的类型现在都不存在，文档里不链到假文件。

### 5.1 冻结快照

拟新增 `ArcBandSnapshot`。在 `prepareGroup` 冻结，创建实体前就写好，之后只读：

- `origin`、`aim`、斩面法线、起始 `gameTime`
- `groupId`、份序号、这一组使用的拍号
- 半径、半宽、扫角起止、滚转。半径和半宽在 `prepareGroup` 里已经乘过一次最终 scale

世界坐标由此冻结。之后移动、转头不改这份快照。实体要用的快照在创建之前写好，不在 `commitGroup` 之后才第一次写入。

原点取值：

- 普通挥砍：准备瞬间的眼睛侧挥点，只采样一次。
- 索敌：只把冻结 `aim` 设为当时目标中心方向，不搬 `origin`，飞行中不追踪。
- 落点、交错：用该份自己的 `overrideGeometry` 原点。
- 动作：用接触位置和接触方向的快照。
- 一分为三：每一份用自己的位置，同一 `groupId`，同一拍号。

禁止在生成循环里因为原点暂时为空就改读玩家实时眼位。没有覆写时，眼位也只在准备前采样一次再写入快照。

撰写时，`trajectoryMutable=false` 会连同绑在一起的 `acceptsTargetOverride()` 变成 false。[WaterReleaseDefinition.java](../src/main/java/com/bslx/XueXiMod/shu/technique/release/WaterReleaseDefinition.java) 当时就是这样返回的。`SkillChainPlan.lockThisCast`（撰写时约第 463 行）和 runner 的 `entityLock && mutable` 门会把水刃的初始瞄准挡掉。这是审计基线，不把它写成今天的绑定事实。

拟新增两个分开的能力。其他术式不声明时，仍按现在的 `trajectoryMutable` 同时决定初始瞄准和轨迹覆盖：

- 接受初始目标瞄准：水刃显式为 true。
- 允许轨迹覆盖：水刃显式为 false。垂落、涡旋、追踪都进不来。

统一解析点在绑定快照之前 resolve 目标，把方向写入冻结 `aim`，不改生成原点。不能只在 `TechniqueHitSpec` 里塞一个 aim 就当成接通，也不能写 `water_blade` 的 id 特判。落点和交错只改快照原点与该份朝向，不把路径改成 `STILL` 盒子。

### 5.2 同源弧带

拟新增 `ProgressArcBand`。服务端碰撞和客户端网格都调用它，禁止各写一套角度。

```
point(snapshot, progress):
    angle = lerp(startAngle, endAngle, progress)   // progress 仅在 0..1 的有效挥斩上
    切向 = 绕冻结法线旋转 aim
    return origin + 切向 * radius

ribbon(snapshot, progressFrom, progressTo):
    沿弧取上一采样到本采样的窄带，半宽 = halfWidth
    大跨度时细分，直到弦长 <= 半宽 * 2，或步数达到 8
    用这段窄带测目标 AABB（分离轴或薄胶囊对盒）
    禁止用目标中心点，禁止用整扇粗盒直接算命中
```

主动伤害区间是年龄 `[0, 6)`。进度 0 对应年龄 0，进度 1 对应年龄 6。每次服务端更新先把上一已处理进度扫到 `min(age, 6)` 的末端，再标记是否结束。年龄跨到或超过 6 时，必须先补上直到 6 的最后一段，且只补一次。禁止一看到 `age >= 6` 就返回而漏掉末段。`damageClosed` 之后不再产生新的伤害扫掠。从这一刻到第 10 tick 只渲染断水余流。

```
onServerTick(snapshot, age):          // 拟新增在弧带更新上，不是现有 API
    if damageClosed:
        只渲染余流
        return
    sweepTo = min(age, 6)
    if sweepTo > lastSwept:
        ribbon(snapshot, lastSwept / 6, sweepTo / 6)
        lastSwept = sweepTo
    if age >= 6:
        damageClosed = true
```

每个真实份对每个目标沿用 `hitOnce`：最多一次。一分为三的三份若扫到同一目标，仍按现有份数汇总和无敌帧，不能清除无敌帧来保证三下都进血。余流网格不调用 `ribbon`。

### 5.3 客户端姿态

原版只有一次 `swing`，给不出左斜、右斜、横斩。拟新增 `WaterBladeSwingPose`：读命中体上同步过来的拍号、起始 tick、冻结平面，在第一人称手臂和第三人称持剑模型上叠同一进度。

拟在命中体同步数据增加这三项。撰写时还没有这些字段，也没有三套剑姿，实现时不要写成「已有动画只要切换」。当前已有弧带快照、`ActionCommit` 的挥斩帧和运行时上下文，水刃三拍经动作桥接到第一人称和第三人称渲染。这不是完整蒙皮，游戏里还没看过。

远端弧播放时，人物姿态仍用同一平面角，但原点在远端。姿态表达的是这一拍的挥法，不保证剑身模型与远端水带重合。

### 5.4 持剑资格

拟在释放定义上增加载体要求，默认空。只有水刃声明「主手物品是 `SwordItem`」。装配拒绝、客户端提示、服务端预检调用同一个函数。判断写在定义上，禁止按 `water_blade` 的 id 特判。斧、镐、锄、铲、三叉戟上的其他剑技仍走 `SkillCarrier.acceptsSwordSkill`，不把全部旧 `SWORD` 收成剑。

整链载体预检放在 [SkillUsePacket.java](../src/main/java/com/bslx/XueXiMod/network/SkillUsePacket.java) 当前约第 169 行切 `slice` 之前，也在扣费、拍号推进和延迟调度之前。这样持斧的链不会先放出前段 A，到水刃段才发现不合格。任一术式不满足时整链拒绝：不扣费、不推进、不调度、不进冷却。

异步真正提交（含双重的后半段）再复核当前仍持剑，且原会话仍有效。复核失败时：不生成该成员的弧，不推进该成员的拍号，不刷新衔接窗口。已成功的前段保留。父会话已经确定的冷却、链游标和失败结算，沿公共 `reject` / `cancel`。该成员尚未消费的预算，用公共支付 receipt 退回原来源。不另建退款底座，也不把已经成功的 A 回滚掉。晚期失败不能说成「整链没扣费、没冷却」。

旧法杖上含水刃时，提示：「水刃已改为剑技，请取回并装入剑技槽」。同一玩家建议 40 tick 内只发一次。现有「剑术不能由法杖释放」不要对这条迁移链刷屏。

### 5.5 拍号状态

落地类是 `WaterBeatLedger` 和 `CastSource`，不是链游标，也不占用 `xueximod_chain_step`。`tracksBeatCycle()` 默认关闭，只有剑形水刃打开。请求通过持剑预检后创建不可变父 `CastSource`，显式交给普通 `HostCast`、动作计划 `SkillChainPlan.firePaidPlan` 和水刃会话 `CastExecutionSession`。延迟开账只用这份父源，不读主人最近一次按键。`commitHostGroup` 在复制前按父源准备一次候选；对不上当前主手就让上下文失败，沿原有失败回执退一次预算，不在成功回调里才发现失配。效果读这个候选写进 `ArcBandDraft`。整组真实提交后，`notifyCommit` 只提交已经验证的候选，并用最终 `ArcBandSnapshot.forwardAxis()` / `normalAxis()` 填 `ActionCommit.framed`。双重里原先不进宿主组的成员，由第 0 份复制打开自己的父释放，后一份不再各算一拍。下面仍是这套账的规则，不是第二套接口。

服务端对同一玩家的拍状态串行处理。跨组的提交顺序按实际提交时刻确定。只有同一 tick 上并行的不同组，才用第 2.3 节的稳定序号消除歧义。

```
prepareGroup(player, slot, carrierId, groupId, now, copies):
    if groupId 已有结果:
        返回那份快照，不再生成
    beat = 该键上的候选拍；没有则 0
    if 载体身份变了，或死亡、换维已清: beat = 0
    if now - commitTick > 40: beat = 0      // 间隔恰好 40 仍用当前拍
    冻结整组快照：各份自己的原点，同一 groupId，同一 beat
    半径和半宽只在这里乘一次最终 scale
    返回待发布快照。此时不推进 beat

commitGroup(groupId):
    仅当该组全部分都已创建并发布，且成功条件可判定
    才写入拍状态：beat = (beat + 1) % 3，记下 commitTick 与 groupId
    再次回调返回已提交结果，不再生成

rejectGroup(groupId):
    整组失败，或部分份创建失败：沿公共事务清理
    不留下已经能攻击、却还没记账的实体
    不推进 beat，不刷新窗口
    失败条件必须可判定
```

快照在 `prepareGroup` 写完后才创建实体。`commitGroup` 只确认记账，不负责第一次填写实体要用的几何。双重的 B 要等它自己的 +5 tick 提交点再 `prepareGroup`，不能在 A 成功时预支 B 的拍。B 若按公共失败政策不再调度，水刃不为它补记一拍。

### 5.6 墙（建议，可后做）

若做：方块采样和 `ProgressArcBand` 用同一分段，碰到固体就把该段之后的有效带裁掉，网格停在同一点。若不做：保持水刃命中体当时的阻挡行为，文案和验收都不能写「墙后打不到」。

## 6. 规则组合与迁移

### 6.1 和现有链的组合

结算顺序仍是索敌 → 弹道 → 规则 → 攻击。水刃仍是 `ATTACK`。

| 规则 | 水刃上的结果 |
| --- | --- |
| 索敌 | 只在绑定快照前把冻结 `aim` 写成当时的目标方向。生成点不动，飞行中不追踪。找不到目标就沿用当时准星，并沿用现有清标记 |
| 落点、交错 | 改该份快照几何。弧照样扫，不变成垂落 |
| 一分为三 | 三份各有位置，一个 `groupId`，拍号一次。伤害汇总沿现有公共 tally |
| 双重 | 费用归公共执行计划。每个独立水刃宿主按自己的提交成功推进一次：A 当刻，B 在 +5 tick。冷却仍由父计划在真实释放结束后，把双重、A、B 累加并统一启动一次；期间忽略子术式冷却等待。不改 [双重释放调整意见与实现指导-2026-10-23.md](双重释放调整意见与实现指导-2026-10-23.md) |
| 动作触发 | 接触快照生成独立组。父动作冷却仍一次。动作加双重时，有碰撞则当刻 A、5 tick 后 B，多次碰撞各自开组，父动作的四术式冷却只合计一次；没有碰撞时只有动作冷却 |
| 聚能 | 与定义能量、附魔半径倍率汇成一个 scale，只在快照准备入口乘一次。已缩放快照不再乘。伤害和次数不另加 |
| 潮湿 | 接触时 `HitPayloads` 先加 6。本轮不改公共 payload 时序 |
| 水势 | 水刃声明垂丝同一重水档：每有效份 20、门槛 26、潮湿 6，`momentumSpend` 仍是 0。20 和 26 是垂丝实施取值。普通一按预留 20，一分为三按真实份数预留 60，双重每个成员独立，动作每次成功宿主组独立。不足时整组普通照放。整组生成失败就释放预留，不扣。成功只提交一次，命中不再扣。真实伤害仍可能按公共规则回势，所以界面净变化可以少于 20。湿目标必须在本组第一次接触前已经达到 26。不额外增伤 |

其他 `trajectoryMutable==true` 的术式不改登记。

### 6.2 旧法杖、旧石、旧知识

旧法杖 NBT 不静默删除，也不自动装进任何一个剑技槽。打开或关闭装配都不复制、不丢失。

不兼容的旧水刃走拟新增的专用取回入口，本版不开放「先拿到光标、稍后再删源」。光标上若已是可用石，晚删源会复制一份。若将来要支持光标取回，必须先有转移锁或不可用占位，以及关闭、断线时的回滚事务；那是后续扩展，本版不做。

专用入口在服务端核对原条目的身份和版本，再原子转入背包或术式收纳：

- 目标成功接收之后，才消耗法杖上的那一条源。
- 任一步失败，源和目标都保持不变。满包、重复请求、中途取消都走这条。
- 只移动这一条，保留原 id、胚胎、数量，以及其余术式的顺序。不另造一份返还物。收纳侧同 id、同胚胎的合并仍沿 `SkillStorageData.add`，但失败时连这次合并也不留下。
- 禁止先 `remove` 整表再按类型过滤回写。

取回之后，新的装配拒绝仍然有效：剑术不能再放进法杖。玩家自己把取回的石头装进持剑的剑技槽，走普通剑技装配。服务端不自动迁入剑槽。

术式石和收纳箱里的 `water_blade` 不用销毁、不用重发。

`Learned` 不按类型分成两个集合，登录也是按复杂度 0 的 id 补学。不写知识迁移，不重发物品。类型改完后，新的使用次数进入剑术等级；按 id 存的旧使用次数留在 `water_blade` 上。界面按类型筛选时，水刃出现在剑术列表，这是类型变化后的展示，不是删档。

## 8. 验收

自动测试和构建证据见 [动作构建验证说明](动作构建验证说明-2026-10-24.md)。那些通过不等于下面的实机验收完成。游戏没有启动，实机视觉、多人和当前客户端的 Mixin 注入都还没验。下面每一条仍不勾选。

- [ ] 首次整链预检时主手不是 `SwordItem`：水刃单独或在链中都不生成、不扣费、不进冷却、不推进拍号。持斧的链在切 slice 之前就被整链拒绝，前段不会先放。
- [ ] 已接受并预留预算后换手或会话失效：该成员不生成、不推进；未消费预算经公共 receipt 退回来源；已成功前段、父会话冷却和链游标保留。这种晚期失败不等于整链没扣费、没冷却。
- [ ] 斧、镐等旧剑技载体上的其他剑技仍能释放。
- [ ] 法杖链里任意位置有水刃时，整链不释放，前段法术也不出手。提示是「水刃已改为剑技，请取回并装入剑技槽」，连续按不会刷屏。
- [ ] 打开、关闭法杖装配不复制、不丢失。旧水刃仍在原位置，id、胚胎、数量和其他术式顺序不变，也不会自动进入剑槽。
- [ ] 专用取回：服务端对上原条目身份和版本；背包或收纳成功接收后才消耗源。满包、重复请求、任一步失败时源和目标都不变，不会出现第二份。本版不能把可用石先拿到光标再晚删源。

## R01 — 绑定打开装配菜单时的法杖

定位：[SpellAssemblyMenu.java](../src/main/java/com/bslx/XueXiMod/gui/SpellAssemblyMenu.java)，构造槽83/87行、`stillValid`162行、`writeGear`205行。
触发：拿法杖A打开菜单，在背包界面用数字键等交换主手为B，再改变装配格。
根因：gear来自A，但写入时重新取当前主手；B旧技能被清空，A数据仍在，副本写入B。
本项仅针对保存在物品NBT的法杖；剑技依旧保存在玩家 `PlayerBoundSkills`。

推荐执行：
- [ ] 服务端绑定打开时的法杖对象和所在物品栏位置，明确身份校验策略。
- [ ] 阻止普通点击、数字键、快捷移动、丢弃等移动或替换被绑定法杖。
- [ ] 每次槽位变更前验证对象身份、物品类型及容量；失效时拒绝操作并关闭菜单。
- [ ] 校验须早于槽位变化，避免物品已被扣走、写入才拒绝的半完成状态。
- [ ] 不以NBT相同代替身份相同；仅修改 `stillValid` 不足以保证同一次点击安全。

验收：
- [ ] A/B装不同术式，逐一尝试点击、数字键、Shift、丢弃和主手变化。
- [ ] A、B及收纳术式总量守恒；无复制、覆盖或消失；重新打开和重登后仍一致。
- [ ] 剑技四槽行为不回归；正常法杖装拆、移动和不同容量法杖均通过。

## R02 — 分离旧匣迁移提交与新石插入

定位：[PlayerSpellStorage.java](../src/main/java/com/bslx/XueXiMod/player/PlayerSpellStorage.java)，`migrateOne`102行，`insertOne`116、120—123行。
触发：已有26格，旧匣A迁移占第27格，随后右键新石B。
根因：迁移已删除旧匣A的来源NBT，新石插入失败直接返回，迁移后的玩家收纳没有保存。

推荐执行：
- [ ] 最小修复：迁移独立完成并保存，之后B插入失败不回滚或丢弃A。
- [ ] 如采用完整事务式方案：在副本计算新收纳及各旧匣余量，验证后一次提交内存状态。
- [ ] 审查所有 `migrate` 调用者，统一成功、部分迁移及空间不足时的提交规则。
- [ ] 失败不消耗新石；迁移只移动已接纳数量，剩余旧源保留。
- [ ] 不承诺磁盘崩溃级事务，也不宣称可自动找回此前已丢数据。

验收：
- [ ] 26格+A迁移+B插入：B保留，A落入第27格，重登后存在。
- [ ] 覆盖全满、部分迁移、多个旧匣、重复调用和无旧匣情形。
- [ ] 每次记录新收纳、旧匣和背包的术式总数，前后守恒。

## R03 — 补齐末段冷却与可重放时刻

定位：[SkillUsePacket.java](../src/main/java/com/bslx/XueXiMod/network/SkillUsePacket.java)，处理入口121—126行，`executeSkill`358行附近返回。
触发：单个长冷却末段，例如让锋，紧邻tick重复按释放。
根因：入口以最后开始时刻设置限制，末段自身冷却未完整纳入。
不能扩大为所有分支都没有冷却；`SkillFollowCast` 已有独立busy机制。

推荐执行：
- [ ] 先确定冷却起算点与持续效果重叠政策，见文末决策表。
- [ ] 计划结果分别表达实际开始、结束、允许重放时间，避免一个整数兼任多个含义。
- [ ] 使用服务端绝对tick计算允许重放时间，包含末段所需限制。
- [ ] 与跟随释放busy协调，避免同一段冷却重复叠加。
- [ ] 处理拒绝、资源不足及取消，不能留下永久锁或资源预留。

验收：
- [ ] 单让锋相邻tick释放，记录接收tick、开始tick和下次允许tick。
- [ ] 覆盖单攻击、多段、持续、冲刺、蓄力取消、死亡和换维度。
- [ ] 约定到期可释放，未到期拒绝；不简单把所有持续时长与冷却相加。

## R04 — 所有后续计划服从累计startTick

定位：[SkillUsePacket.java](../src/main/java/com/bslx/XueXiMod/network/SkillUsePacket.java)270行；[SkillChainPlan.java](../src/main/java/com/bslx/XueXiMod/network/SkillChainPlan.java)152、174行。
触发：A攻击后接修饰，再接B攻击，或双重释放位于已有等待之后。
根因：外层已经累计 `startTick`，内层计划从当前now重新安排，后续段提前执行。

推荐执行：
- [ ] 将绝对开始tick传入 `firePlan` 及双重释放等计划方法。
- [ ] 组内相对间隔基于传入时刻，不能重新从服务端当前tick计算。
- [ ] 与R03共用时序结果，但各自保留独立验收证据。
- [ ] 调度执行前保留存活、维度、取消及资源检查，明确清理责任。

验收：
- [ ] A→修饰→B记录实际tick，B不早于累计开始时间。
- [ ] 双重释放组内攻击仍按约定相隔10tick，修饰不占攻击拍。
- [ ] 覆盖冲刺带攻击、蓄力、延迟期间死亡/换维度和资源不足。

## R05 — 持续攻击按共享伤害轮次结算

定位：[ReleaseBatch.java](../src/main/java/com/bslx/XueXiMod/shu/technique/release/ReleaseBatch.java)，`Tally.record`128行、`seenCopies`129—131行、`flush`152及165—167行。
相关：[HeatBeamEffect.java](../src/main/java/com/bslx/XueXiMod/shu/technique/effects/HeatBeamEffect.java)35行；[TechniqueHitSettle.java](../src/main/java/com/bslx/XueXiMod/shu/technique/release/entity/TechniqueHitSettle.java)95行。
触发：一分为三+热光束，对同一目标持续至少三轮。
根因：副本序号跨整段持续时间去重，第一轮后该副本永久被视为已结算。

推荐执行：
- [ ] 引入显式round标识，按释放组、轮次、目标和副本去重。
- [ ] 区分伤害轮次、轮内去重、首个有效命中后约6tick的汇总窗口。
- [ ] 单次攻击采用固定轮；持续攻击采用组共享时基或明确的共享轮次协议。
- [ ] 不采用各副本自己的命中计数作轮次，否则漏打会让轮次错配。
- [ ] 每轮结算后保留已结算状态防迟到重复，生命周期结束再清理。
- [ ] 不在flush时简单清空 `seenCopies`；10tick命中周期与6tick汇总窗口是不同概念。
- [ ] 不顺带修改无敌帧。

验收：
- [ ] 同一目标至少三轮，各轮份数与伤害正确。
- [ ] 覆盖某份漏打、迟到超过6tick、跨轮边界、多目标和同份重复回调。
- [ ] 普通光束、单次飞弹及未使用一分为三的攻击保持原行为。

# 让锋真实分水：修改与实现指导

现行显示名（2026-11-03，仅改名）：这项功能的玩家显示名是断潮，稳定 ID 仍是 `water_yielding_ribbon`。文件名和下面正文保持原样，文中的「让锋」指同一项已实现功能。

日期：2026-10-26。面向下一位改代码的人。本文只定接入方式。本轮未改功能、未编译、未进游戏、未打包。此前任何潮湿相关试玩都不能当作本功能已通过。

水牢设计不在本文范围，做完分水接入后再单独做。

## 1. 目标

让锋（`water_yielding_ribbon`）保持现有斩击：伤害、挥斩时机、链上冷却、附魔、一分为三的 `ReleaseBatch.Tally` 与无敌帧都不因这次环境功能改动。命中体积保持现在的长 7、宽 0.7、高 3.2，不把攻击盒扩成水通道。

在此之外，释放成功并真正改到世界水时，开一条临时干通道：全宽 3 格，长度与方向跟这次实际斩击，整段水柱从连续水面一直处理到固体或世界底界，没有固定深度上限，不挖掉固体地形。通道维持 200 tick（10 秒），之后让原版水自己流回。改的是服务端真实方块，不是粒子，也不是只在客户端藏水。

没有永久干沟。不附带通用攻击范围或伤害加成，也不把旧的重水控制接回来。

## 2. 已确认规则

以下是用户已确认的玩法，实现不得放宽。

- 新建分水操作时，可用水势必须严格大于 50。等于 50 不合格。现有 `WaterMomentum.reserve` 在 `requested > available + 0.001` 时才拒绝，因此 `available == 50` 时 `reserve(50)` 仍会成功。调用方必须先判断 `available > 50`，再预留 50。同一操作只预留这一次。
- 一次操作最多扣 50，与改过的方块数无关。没有实际改变水体则不扣这 50。
- 通道全宽固定 3。长度与方向取实际斩击，不取登记里的 32，也不取客户端水面贴图。
- 从斩击真正碰到的连续水体向上找到水表，再向下直到固体或该维度最低建造界。不相连的另一片水不要从世界顶部另抓。
- 干通道保持 200 tick，然后自然回流。不替换、不破坏固体地形。

## 3. 现状（已核对的代码事实）

让锋没有单独的水面实体。`WaterYieldingEffect.execute` 只调用 `TechniqueHitSpec.spawn`，生成 `TechniqueHitEntity`（`visual = 6`）。客户端 `WaterPartingRenderer` 只画贴图。

登记在 `ReleaseDefinitions` 第 21 行：`cohortSword("water_yielding_ribbon", …, 32, 0f, 0.55f, …, ATTACK, false, false)`。这里的 32 是 `lifetimeTicks`，不是距离。效果自己也不读这份寿命、不读 `thickness = 0.55`，也不读 `spanScale` / `lengthScale`。效果内另有 `LIFETIME = 32`，写进 `spec.lifetime`。`trajectoryMutable` 为 false。

`ReleaseRegistry.HOST_GROUP` 只有 `space_cut`。`submitsHostGroup("water_yielding_ribbon")` 为 false。让锋不走宿主组回执。`WaterYieldingEffect` 丢掉 `SpawnReport`。`SkillSegmentRunner.commitNow` 在 `runSegment` 返回后把释放标成已提交，不看实体是否进世界。因此不能把现有提交回调当成「斩击已生成」。

无落点、无交错、无动作接触时，`CastFrame.forAttack` 令 `overrideGeometry = false`。效果用压平后的 `cast.getLook()`，锚点是脚点加水平前向 1.15、再抬高 1.15，`path = STILL_AIM`，`centered = false`，`length = 7`，`width = 0.7`，`height = 3.2`，`hitReadyAge = SURFACE_TICKS`（10）。`StillAimMotion.tick` 把实体放到锚点再沿水平前向前进 `length / 2`。攻击段从锚点伸到前方 7 格，全宽 0.7，全高 3.2。落点或交错改走居中几何，锚点与朝向被帧覆写，效果里的 1.15 偏移不再有效。动作接触把原点写成接触点，朝向写成接触方向的水平分量。公共体积缩放发生在 `TechniqueHitSpec.spawnReported`；让锋自身能量缩放与半径乘子都是 1，但快照仍应读缩放之后的实体。

服务端 `TechniqueHitEntity.tick` 先 `age++`，`age >= hitReadyAge` 才 `TechniqueHitSettle.tryHit`，`age >= lifetime` 时 `onExpire`。首次可攻击是 age 第一次达到 10。约 32 tick 后实体结束。音效用服务器 tick+10，与 `age` 不是同一只钟。分水寿命远长于斩击，必须放在独立服务里，不能挂在命中实体的 32 tick 上。

客户端水面单侧宽、裂开间隙、辉光半宽都只影响绘制。分水长度只读激活时实体的 `position()`、`forward()`、`length()`。

水势余额在 `PlayerShuData`，NBT 键 `xueximod_shu_data` 的 `WaterMomentum`，写入夹到 0–100。预留是 `WaterMomentum` 的静态表，不存档。

- `available(ServerPlayer)`：余额减去该玩家仍为 `RESERVED` 的预留。
- `reserve(ServerPlayer, float)`：合法且额度够则 `RESERVED` 并入表。金额不大于 0 时返回已是 `COMMITTED` 的 `Hold`，`accepted()` 为真，但不进表。
- `commit(ServerPlayer, Hold)` 无返回值。空、非预留或 UUID 不符直接返回；不符时这笔继续占额度。成功才出表并扣余额。
- `release(Hold)` / `releaseAll(UUID)` 只放走 `RESERVED`。
- `PlayerMomentumPurse.commit` 只要参数是 `Hold` 就返回 true，底层没扣也如此。`spawn` 的返回值、`commitNow`、这个 `commit` 的 true 都不是分水成功证明。

死亡、下线、换维经 `ReleaseBaseEvents.endCast` 到 `ChargeGate.interrupt`，只 `releaseAll`。已扣余额不退。停服不会调用 `releaseAll`；未提交预留随进程消失，也不会补扣。

本次在 `src/main` 的 Java 里没有找到可复用的临时改水 `SavedData`。`MagicCreateWaterEffect` 只是永久放水源。只把水格设成空气，旁边的水大约 5 tick 就会流回，挡不满 200 tick。

原版事实来自本机 Forge 1.20.1-47.3.33、Parchment 2023.06.26 的映射源码，供实现时对字节码，不是已验证的 Mixin。`Fluids.WATER` 是水源（`isSource` 真，水量 8）。`Fluids.FLOWING_WATER` 不是水源。整格水是 `LiquidBlock`。含水方块不是液体方块：台阶、楼梯等含水为真时流体仍是水源，方块本体还在。`FlowingFluid` 在流体 tick 后会扩散；整格被设成空气后，邻居液体会再预约流体 tick。海绵、水桶、`pickupBlock` 都会拆植物或改别的块，不能拿来当分水。

## 4. 推荐规则（用户尚未单独确认）

下面是接入时建议直接采用的默认，文档已写完整，不必再等确认。实现注释和交接里仍要标明它们是推荐，不是已确认玩法。

- 一分为三：同一宿主释放的三份共享一个操作，几何取真实斩击的并集，整次最多扣 50。复制序号不进入操作身份。不要用 `settleCopyIndex`、`Tally` 对象或「玩家 + tick」当身份。效果侧先 `getOrCreate(operationId)`。只有新操作才判断 `available > 50` 并 `reserve(50)`；同 id 的后续复制只附加几何和生成结果，不重新资格、不重复预留。水势上限是 100。余额 80 时，首份预留 50 后可用为 30，其余复制仍必须附加，不能因为不再大于 50 而被拒绝。同一操作在同一 tick 可激活的几何先合并，再做唯一一次首次提交。
- 双重释放：两个宿主各算各的操作，可以各扣 50。各自的动作接触组也彼此独立。
- 新释放只扫过旧干通道、没有新的水体被改掉：不扣费，也不给旧通道续期。
- 确实改到新水并完成提交：只为这次新改到的格子取得租约。先前留下的干空气不能记成「待恢复水源」。
- 含水方块与水生植物首版保护：不改含水属性，不拆海草、海带。这些格子是保护边界，该柱不保证完全干燥。只移除纯水液体块。以后若要排含水，另定植物存活与恢复。这条限制必须让测试看见，不能藏进实现细节。
- 玩家死亡、下线、换维发生在提交之前：取消未提交操作并释放预留，世界应尚未留下已提交的干通道。提交之后不退款；200 tick 通道继续走存档，不因玩家离开立刻灌回。异常停服见第 8 节，不能当成跨文件原子事务。

## 5. 拟新增类型

下列类型现在都不存在。名字是建议，包可放在 `com.bslx.XueXiMod.shu.technique.release.parting`。不要写成已经有的类。

- `PartingOperationId`：一次分水操作的身份。
- `PartingGeometrySnapshot`：激活时冻结的水平前向、真实中心、半长、全宽 3、竖向接触范围。
- `PartingOperation`：状态与预留、快照、扣费结果。
- `PartingCellLease`：一格的原状态、预期临时状态、所属操作、是否仍由服务控制。
- `WaterPartingService`：资格、激活、扫描、改水、阻水、到期。
- `WaterPartingSavedData`：拟新增的维度级存档，经对应 `ServerLevel` 的 `DataStorage` 取得，保存已提交租约与到期游戏时间。
- 拟新增水势方法，例如 `WaterMomentum.commitReserved(ServerPlayer, Hold)`，返回是否真正从 `RESERVED` 扣到余额。保留现有 `commit` 与 `PlayerMomentumPurse.commit`，不重构账本。

让锋只在 `WaterYieldingEffect` 显式启用分水。通用释放路径只负责发放操作身份和「实体 age 第一次达到就绪」的通知。其它术式不因为 id 判断被拉进分水。

## 6. 操作身份与几何快照

身份在通用释放入口生成，建议落在已经区分宿主、双重成员和动作接触的位置（`SkillSegmentRunner.runSegment`、双重序列、`CastExecutionSession` 的接触组附近），再交给本段效果。

- 父释放一个 token，加上宿主或双重成员序号。一分为三的 `copyIndex` 不写入这个 id，三份因此自然共享。
- 每个动作接触沿用它已有的接触组区分，不同接触组不要合成一次扣费。
- 效果先 `getOrCreate(operationId)`。新操作才做资格和预留；同 id 的后续复制只把本份几何和生成结果附加到已有操作。`TechniqueHitEntity.tick` 在 `age` 刚跨过 `hitReadyAge` 时发一次通用通知。服务把同一操作、同一 tick 里因此可激活的几何合并成一份，再进入首次扫描。没有登记则什么都不做。
- 激活时刻是该实体 `age` 第一次达到 10，不要用释放时的 `serverTick + 10` 去猜。落点、交错、动作若改变了放置，快照会跟着实体上已经放置好的中心与前向。
- 快照在公共缩放和 `StillAimMotion` 完成本拍放置之后读取：水平 `forward()`、实体 `position()` 作为真实中心、`length()`。通道两端是中心加减 `forward * length / 2`。全宽 3，与攻击宽 0.7 无关。竖向只记录斩击当时覆盖到的水体，用来寻找连续水柱的起点。
- 方块是否落入通道：方块水平中心落在该有限矩形内。这是推荐的确定规则。
- 快照一旦写入操作就不再跟随玩家镜头或准星。之后视线转动不能把已经定下的方块通道带走。

水柱从快照里的竖向接触找起，而不是从世界顶向下扫：

```
对通道内每个水平格 (x,z)：
  在斩击竖向覆盖里找实际碰到的纯水液体块，记为触点
  没有触点则该柱跳过
  从触点向上，连续的纯水走到水表；遇固体或非纯水停止
  从水表向下，连续纯水直到固体或该维度最低建造界
  含水方块、海草、海带整格跳过，不改属性
  未加载的区块整段留到加载后，沿同一快照再扫
```

## 6.1 已核对的现有签名

实现时直接调用这些现有方法。拟新增方法不要冒用它们的名字。

- `WaterMomentum.available(ServerPlayer)`、`reserve(ServerPlayer, float)` 返回 `Hold`、`commit(ServerPlayer, Hold)` 无返回值、`release(Hold)`、`releaseAll(UUID)`。`Hold.accepted()` 在 `RESERVED` 或 `COMMITTED` 时为真。
- `PlayerMomentumPurse.reserve(float)` 在金额不大于 0 或未接受时返回 null；`commit(Object)` 对任意 `Hold` 返回 true。
- `WaterYieldingEffect.execute(ServerPlayer, Technique, ItemStack, TechniqueCastContext)`。`TechniqueHitSpec.spawn(ServerLevel, ServerPlayer, TechniqueHitSpec)` 丢掉回执；`spawnReported(...)` 返回 `SpawnReport`，`complete()` 为 `requested > 0 && accepted == requested`。
- `TechniqueHitEntity.tick` 内 `age++` 之后才做 `age >= hitReadyAge` 的命中。`length()` / `forward()` / `position()` 在放置之后才代表真实斩击。
- `ChargeGate.interrupt(UUID)` 只释放仍为预留的水势。

某一份生成失败（`SpawnReport.accepted()` 为 0，或该份实体没有进世界）时，不把这名实体挂上。操作里从未挂上实体且仍未提交时，才 `release` 仍为 `RESERVED` 的 `Hold`。已挂上的实体在 age 到 10 之前全部消失，或玩家在提交前死亡、下线或换维：取消未提交操作，只 `release` 那一笔 `Hold`。同 id 的其它成功复制不因此另做预留。

## 7. 状态机

```
准备
  getOrCreate(operationId)
  已有操作 → 只附加本份几何与生成结果，不判断水势，不再次 reserve
  新操作且可用水势 > 50 → reserve(50) 得到 RESERVED
  新操作但可用水势不大于 50 → 只放原斩击，不建分水操作
预留
  本份 spawnReported 确认实体进世界 → 挂到该操作，已生成待激活
  本份生成失败 → 不挂这名实体
  从未挂上实体且仍未提交 → release，结束
已生成待激活
  同一操作、本 tick 第一次跨过 hitReadyAge 的几何先合并
  合并后的快照进入首次扫描
  激活前实体都消失，或提交前被打断 → release，结束
首次扫描
  只读已加载区块，收集纯水液体格
  先登记可恢复意图，再装上暂定租约
  确认 Hold 仍为 RESERVED，且至少 1 格改成空气 → 唯一一次 commitReserved
提交并维持
  commitReserved 为真 → 200 tick 从这次提交的维度游戏时间起算
  续批只查操作已提交、未到期、候选合法，不再 commitReserved
  首次 commitReserved 为假 → 只回滚这一批未提交的暂定改动并 release
  续批失败 → 停止未完成工作；不退款，不撤销其它有效租约
到期释放
  最后一个租约到期后，按第 8 节恢复
```

无水、首次扫描 0 格成功、或首次提交时 Hold 已不是 `RESERVED`：取消，不扣费，也不留下免费干通道。扫描可以分批，但在第一次真实扣款成功之前，不能把改块留到后面的 tick 变成永久空洞。第一批「真实改水 + 唯一一次 `commitReserved` 成功」构成已提交操作。续批共享这笔费用，不要求旧 Hold 仍为 `RESERVED`，也不再调用 `commitReserved`。续批失败只停止尚未完成的工作，不按从未成功退款，也不撤销其它已经有效的租约。未加载区块不强加载；加载后按同一冻结快照补扫，仍算这笔已提交操作。

严格大于 50 只用于新建分水操作的 `reserve(50)` 之前。水势上限是 100。余额 80 时首份预留 50，可用变为 30，同 id 的复制仍然附加。同一服务器线程上，偏转和分水共用 `WaterMomentum` 的预留表，预留占住的额度不能再花一次。分水预留之后，普通偏转仍按既有潮湿动态门槛和报价预留；剩余够付那次报价就继续，不能因为剩余不大于 50 就禁止偏转。

## 8. 真实阻水、恢复、重叠

只在服务端处理水，且只处理活动租约。不阻挡实体移动，也不改通道外的流体。

推荐用格子租约阻止水重新进入，而不是每 tick 把格子再设成空气，也不要放隐形实体墙。实现时在本机 1.20.1 字节码上核对下列候选，核对完成前不能声称钩子已运行：

- `FlowingFluid` 里真正决定目标格并写入流体的路径（调查看到的源码区间约 153–186、405–421 行一带）。水要流进目标格之前，若该格有有效租约，则取消这一次进入。
- `FlowingFluid.tick` 原地重算、以及水源再生后的写入（调查看到约 113–129、245–254 行一带）。只拦横向扩散会漏掉原地变成水源。
- 注入点、方法描述符、取消方式以当时 jar 为准。每个注入都要有测试：租约存在时水不进入，租约解除或格子已退出服务后原版流动恢复。

水桶、玩家放置方块等外部修改默认不吞掉。该格退出服务控制，恢复逻辑跳过它，避免删掉玩家的新内容。

改水与扣费在服务器线程上按这个顺序，以便提交前能回滚：

1. 分批扫描已加载区块。改水前先登记可恢复意图：操作 id、原方块状态、来源类别（水源、流水或其它）、预期临时状态、候选位置。
2. 装上暂定租约，并确认格子仍是刚才读到的纯水。首次提交的批次还要确认 Hold 仍是这位玩家的 `RESERVED`。已经提交的续批只确认操作有效、未到期、候选合法，不要求 Hold 仍为 `RESERVED`。
3. 写成空气并记下实际成功的格子。标志需要通知邻居并同步客户端（原版 `setBlock` 的 1 与 2，常用组合是 3）。不要用会拆植物的海绵或桶。
4. 仅首次批次在成功格至少 1 个时调用一次 `commitReserved`。返回真才把这批租约升为已提交，并更新提交状态。续批不再调用 `commitReserved`。
5. 首次 `commitReserved` 返回假：只回滚这一批还未提交的暂定改动（格子仍是本次写入的空气时改回原状态），不撤销其它有效租约。
6. 首次批次成功 0 格：`release`，不扣费。续批失败或没有新的合法改水：停止尚未完成的工作，不按从未成功退款，也不撤销已经有效的租约。

200 tick 用该维度的游戏时间，从首次成功提交起算，不从排队或释放动画起算。停服不消耗剩余时间，加载后用存档里的到期游戏时间与当前维度游戏时间比较。这条必须写进 `WaterPartingSavedData`。

玩家数据与世界SavedData之间没有跨文件崩溃原子性。实现时应先登记可恢复意图，包含操作ID、原状态、预期临时状态及候选位置，再执行改水与扣款，并更新提交状态；setDirty或修改内存记录不等于已经可靠写盘，持久化顺序须在实现期核验。加载后，只处理有有效恢复记录且当前状态仍符合预期的位置；没有记录的空气不得推断为本服务所改，也不得凭空填水。邻水回流取决于周围水源、地形及流体更新，不能保证在约5tick内恢复。即使保留恢复意图，扣款与世界保存之间仍可能存在崩溃窗口，应明确记录其限制与补偿策略，不宣称事务原子性。

每格保存：原水状态、来源类别、预期临时状态、租约 id 集合（或引用计数）。最后一个租约到期时，仅对仍由服务控制、且没有被玩家改掉的格子处理：

- 原状态是水源：状态与归属校验通过后写回水源，并按需唤醒周围现存水流。
- 原状态是流水：不把旧流水逐格画回去；同样按需唤醒周围现存水流，交给原版重算。
- 周围没有可流来的水时，这两类格子都不保证被填满，也不为了填满而新造水源。
- 格子已是别的固体或玩家新块：保持现状，不用历史快照覆盖。
- 原水源周围的水已经不在时，仍只恢复当时确实是水源的那一格，不用整片旧快照铺回去。

重叠：同一格可被多条租约持有。先到期的那条只减自己的计数，另一条还持有时不恢复。原状态以第一次取得控制时的记录为准。

## 10. 验收清单

实现完成前，下面每一条都要在游戏里单独看到结果。本文本身没有编译，也没有做这些测试。

- 新建分水操作时可用水势小于等于 50：斩击照常，没有干通道，余额不变。略高于 50：可以预留。同一操作的后续复制不再做大于 50 的判断。与同 tick 偏转并发时，分水只占住自己预留的额度；偏转仍按既有潮湿动态门槛和报价预留，剩余够付就成功。不能因为剩余不大于 50 就禁止偏转，也不能让两边花同一笔额度。
- 面前无水、生成失败、Hold 在提交前已失效：没有免费通道，也没有扣款。
- 普通释放、落点指定、交错、动作接触：通道与各自实际斩击的中心、前向、长度对齐，不跟后来的镜头移动。
- 一分为三按推荐只扣一次 50，范围是三份真实几何的并集。余额 80 时首份预留 50 后可用为 30，另外两份仍附加，不能被拒。同 tick 可激活的几何合并后只做一次首次提交。双重按推荐分开扣。复制序号不同不能拆成三次扣费。
- 深水一直处理到固体或世界底界；中途固体停止该柱；未加载区块不强加载，加载后仍属同一笔费用。分批改水只在首批成功时扣 50。已提交后的续批不要求 Hold 仍为 `RESERVED`，也不再 `commitReserved`。续批失败停止未完成工作，不退款，不撤销其它有效租约。
- 200 tick 内租约格不被邻水灌回。到期后，原水源在状态与归属校验通过后写回；原流水不画回旧状态。两类位置都按需唤醒周围现存水流。周围没有水时不保证填满，也不造新源。不出现永久干沟。
- 玩家在通道里放的方块保留。重叠的两条通道在第一条到期时，第二条仍占着的格子保持干燥。
- 退出重进、卸载再加载区块：剩余时间按维度游戏时间继续，不在停服期间把 200 tick 走完，也不把未提交预留补扣。维度数据经该维 `ServerLevel` 的 `DataStorage` 取得。没有有效恢复记录的空气不推断为本服务所改，也不凭空填水。邻水回流不保证在约 5 tick 内完成。
- 含水台阶、楼梯、海草、海带保持原样，这些格子可以仍是湿的。
- 同一条 Mixin 或同一次 age 通知重复进入时，不重复扣费，也不重复清除已恢复的格子。
- 不同水深、不同坐标、区块边界两侧，客户端都能看见对应的空气与恢复后的水。
- 伤害、冷却、附魔、一分为三结算、无敌帧、水势偏转的原有提示与这次改水无关，行为保持改动前。

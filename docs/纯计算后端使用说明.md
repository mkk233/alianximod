# 纯计算后端使用说明

Java 参考实现是默认路径。不放动态库、不加启动参数时，游戏仍按原来的轨迹、转向、追踪步长和近战走廊公式计算。本文不承诺 FPS 或 TPS 变化。

## 选择后端

只认两个 JVM 参数，大小写敏感，不写入模组配置：

- `-Dxueximod.compute.backend=java`
- `-Dxueximod.compute.backend=native`
- `-Dxueximod.compute.library=动态库绝对路径`

不写 backend，或写成 `java`，就用 Java。这时即使带了 library 也不会加载。写成 `native` 时，library 必须是绝对路径，文件名必须是：

- Windows：`xueximod_compute.dll`
- Linux：`libxueximod_compute.so`
- macOS：`libxueximod_compute.dylib`

加载器不搜索目录，不从网络下载，也不读取 `java.library.path`。Windows 只接受 64 位 JVM。路径不是普通文件、名字不对、握手版本不是 1，或者加载失败，都会留下 Java 路径。路径里有系统不接受的字符时，只捕获 `InvalidPathException`，原因记为 `library-invalid-path`，同一次解析收束到 Java，之后不再重复抛这条配置异常。其它运行异常和 Error 仍会抛出。第一次进入这些计算时记录一行所选后端或回退原因，之后不按实体重复记录。

2026-10-30 的 Windows x64 动态库是 `native/compute/build/xueximod_compute.dll`（26112 字节，写入 `2026-10-30T08:40:59.0017107Z`）。返修后的官方脚本再次退出 0，Ninja 无工作，DLL 时间未变。Linux 和 macOS 没有对应动态库。同一天最后一次 Java `compileJava` 实际执行并通过。详见文末验证。

## 已经接入的计算

现有方法签名不变：

- 轨迹采样的直线、垂落、跟随视线、涡旋，以及未注册函数时的直线退回。
- 有界转向，以及剑追踪的一步方向和步长。
- 剑前走廊的相交、接触距离和阻挡判断。

已注册的轨迹函数回调、体积贴合、方块射线、实体查询和随机数仍留在原来的 Java 时点。三维交错和一分为三没有接入。

## 单次调用和批量

默认不写 `backend=native` 时，每把剑、每个攻击体仍是一次标量调用，直接执行 Java 公式，不分配批量数组，也不进入 JNI。

显式写成 `backend=native`，并且库路径有效、握手成功、对应能力位打开时，这些已经接入的单次计算会按现有批量布局以 `count=1` 进入对应 JNI。不需要另加开关，也不会复制出 8 条假数据，更不会把当前这一拍推迟去凑批。单条 JNI 可能更慢。这个模式用来接入和对比后端，不表示帧数或 tick 变快。

公开的批量方法仍保留条数下限 8：少于 8 条的批量调用继续用 Java。游戏里的现有适配不走这条批量入口，所以这个下限不会把显式 native 模式下的轨迹、转向、步长和走廊留在 Java。

能力位缺失、返回非 0、加载失败或链接错误时，同一组输入改由 Java 参考实现完成。业务异常会照常抛出。进程被 native 崩溃打下来时，不会被捕捉后续跑。同一条线程的 native 缓冲最多嵌套 4 层；再往里的重入改走 Java，避免和外层共用一块输出。

涡旋已经停驻且起点对象是 null 时，Java 和显式 native 的活调用都先算出停驻方向，再把位置存在标记清掉。`Sample.position` 仍是 null，方向仍是水平前向，不会变成原点。还在旋转时空起点仍抛空指针。数字协议和 C 源没有为此修改。这不是已经成功调用 C 的记录。

## 性能记录

采样仍由原有记录器控制。关闭采样时，这些计算不额外读取 `nanoTime`，也不逐条写日志。打开采样后，summary 会多出：

- 耗时 `COMPUTE_BACKEND`：只包纯计算边界。
- 计数 `COMPUTE_LOGICAL_REQUESTS`、`COMPUTE_JAVA_EXECUTIONS`、`COMPUTE_NATIVE_EXECUTIONS`、`COMPUTE_JAVA_FALLBACKS`。

Java 执行、native 接受和回退互斥，一次逻辑请求只记其中一项。单次调用内部不会再记一笔批量。它们不是元素个数，也不能与原来的运动、几何、窄判定相加。`ticks.csv` 的列没有改。

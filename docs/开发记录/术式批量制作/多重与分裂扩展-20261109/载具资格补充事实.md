## 1. 容量签名

`Skill.CHAIN_LIMIT` 在 `D:/alianximod/src/main/java/com/bslx/XueXiMod/skill/Skill.java` 第 21 行，值是 8。它只出现在剑术装配：`SpellAssemblyMenu` 把 4 条链铺成 32 个格子，第 264–278 行和第 321–327 行用 `slot * 8 + techniqueIndex`；`SkillAssemblyPacket.put` 第 155、171–175 行在非法杖分支拒绝第 9 段。法杖长度不读这个常量。

法杖上限是 `StaffData.SLOT_CAP = 32`（`StaffData.java` 第 5、14–17 行）。测试法杖在 `ModItems.java` 第 27–28 行写成 `new StaffData(32, ...)`。单把法杖的实际格数是 `StaffItem.data().slotCount()`，`StaffSkills.slotCount` 第 62–64 行读取它。

`CastPlanCache.CHAIN_LIMIT = 64`（`CastPlanCache.java` 第 25 行）是计划缓存自己的上限，不是装配格。

四个剑术入口是槽 0 到 3，各存一条链，不拼成一条 32 格链：

- 按键：`SkillHotkeyHandler` 第 58–68 行。使用键发槽 0；槽 1–3 走 `SKILL_SLOT_2/3/4`。手持法杖时槽 1–3 不发。
- 服务端：`SkillUsePacket.offerNow` 第 166–190 行。法杖要求 `slotIndex == 0`，然后 `StaffSkills.asSkill`。否则 `slotIndex` 必须在 0 到 3，再 `PlayerBoundSkills.get`。
- 存档：`PlayerBoundSkills` 第 8–19 行，玩家持久数据 `xueximod_bound_skills` 下的 `BoundSkill_0` 到 `BoundSkill_3`。`Skill.fromNbt` 第 126–167 行按列表全读，不截到 8。
- 装配网格：`SpellAssemblyMenu.fillGear` / `writeGear` 第 263–278、321–341 行，只回写每条链前 8 格。已经长于 8 的链标进 `preservedChain`，这次不改写。

打开装配界面的是 `SkillAssemblyPacket.open` 第 92–108 行，实际菜单是 `SpellAssemblyMenu`，屏幕是 `SpellAssemblyScreen`。非法杖时 `gearSlots` 固定 32（第 76–77 行），也就是 4×8。法杖时 `gearSlots` 等于该法杖的 `slotCount`，再夹在 1 和 32 之间。

`SkillAssemblyScreen` 已注册，但当前打开路径没有创建 `SkillAssemblyMenu`。它的 `computeSlotCount` 第 137–142 行在剑上返回 4，那是四条入口，不是每条 8 段。

## 2. 装配时怎么拒绝

服务端剑术包是 `SkillAssemblyPacket.put` 第 154–176 行：法术进剑槽拒绝，聚能拒绝，装配消耗超上限拒绝，满 8 段拒绝。同文件第 179–188 行再用 `SkillSegmentMath.mixedChainRefusal` 拒绝自身状态或操纵术式混链。这里不看 `multicastSpec`。

法杖包走 `slotCount`（第 150–152 行）和 `admitCandidate` 第 370–401 行：超槽、未学会、剑术进法杖。捕获链另走 `ActorCaptureCarrierGate`。

石头界面的同一套规则在 `SpellAssemblyMenu.rejectReason` 第 349–406 行，`GearSlot.mayPlace` 第 722–726 行调用它。剑术分支只拒法术和装配消耗；法杖分支只拒剑术、满槽和未学会。

客户端没有和这两处共用的资格函数。`SpellAssemblyScreen` 的类型按钮只筛术式石列表。`SkillAssemblyScreen.put` 直接发装配包。隐藏列表挡不住包和 NBT。

## 3. 已保存链释放时

剑术四槽在 `offerNow` 第 178–190 行解码。随后第 195–205 行只查玩家可用和持剑门。法杖才进 `StaffSkills.castRefusal`（`StaffSkills.java` 第 115–125 行）：槽位数、超长保留、未知术式、未学会。第 206–224 行再拒非法杖捕获，以及不能被捕获许可的剑术。两条路都不读 `multicastSpec`。

因此八重、十六重、穷尽只要已经写进某一条 `BoundSkill_N`，现在的释放会放行。`Skill.fromNbt` 也不截断。技能书 `bindBookToWeapon` 第 62–81 行写的是武器自己的 `BoundSkill_N`，释放读的是玩家持久数据，不是这条武器标签。

可复用的公共点是「剑术载具上的这条链」，按 spec 判断，不按三个 ID：

- `multicastSpec() == null`：不因这条新限制拒绝。三重、四重是 `fixed(3)`、`fixed(4)`。
- `kind == REMAINING`，或 `kind == FIXED` 且 `fixedCount() >= 8`：剑术拒绝。
- `replication()` 的 2、5、8 不在这里拒绝。

`fixedCount()` 在 `MulticastSpec.java` 第 33–37 行，种类不是 `FIXED` 时会抛异常，所以要先看 `kind()`。法杖链不要加这道判断。

只改装配不够。释放入口 `SkillUsePacket.offerNow` 在取得剑术 `Skill` 之后、`executeSkill` 之前也要查，否则旧 NBT 可以绕过。

## 4. 最小落点

必改的现有方法：

- `SpellAssemblyMenu.rejectReason`，非法杖分支，约第 386 行之后。这是当前真实装配界面的服务端落子检查。
- `SkillAssemblyPacket.put`，非法杖分支，约第 171 行附近，以及第 179 行已有的整链检查旁。包仍会被处理。
- `SkillUsePacket.offerNow`，第 190 行拿到剑术链之后。这是四条已保存链的释放检查。

没有现成文案能表达这件事。剑术现用的是硬编码中文，例如「无法装配：法术不能装入剑技槽」「无法装配：一条剑技最多 8 段」。`gui.xueximod.staff.sword` 是「剑术不能由法杖释放」，`gui.xueximod.batch.unsupported_host` 是成组释放拒绝，都不能挪用。

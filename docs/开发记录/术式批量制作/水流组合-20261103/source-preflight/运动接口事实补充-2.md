# 运动接口事实补充 2

2026-11-03。只补玩家、载具和重力的本地事实。不是新一轮复审，也不选接入方案。源码包仍是 `forge-1.20.1-47.3.33_mapped_parchment_2023.06.26-1.20.1-sources.jar`。未打开的方法体标为未读。

## 1. 移动包的接受和纠正顺序

包进入主线程的方式：`PacketUtils.ensureRunningOnSameThread`（`PacketUtils.java` 35–54 行）在非主线程时 `executeIfPossible` 后抛出换线程异常。`Connection.tick`（285–290 行）只 `flushQueue` 再调用 `TickablePacketListener.tick`，不在这里取出已入队的移动包。`MinecraftServer.runServer` 先 `tickServer`（679 行），再 `waitUntilNextTick` → `runAllTasks`（683、752–753 行）。因此同一轮里，`ServerTickEvent.END` 先结束，排队的移动包在随后的任务循环里处理。

`ServerGamePacketListenerImpl.tick`（257–304 行）在世界实体 tick 之后、`END` 之前：

1. `resetPosition`（334–340 行）把 `firstGood` 和 `lastGood` 都写成当前玩家坐标。
2. `player.doTick()`（267 行）。`ServerPlayer.doTick`（486–489 行）调用 `super.tick()`，落到 `Player.tick`，不是 `ServerPlayer.tick`。
3. `absMoveTo(firstGoodX/Y/Z)`（268 行），把 `doTick` 期间的位置写回第 1 步记下的坐标。这里不改 `deltaMovement`。
4. 若根载具不是玩家本人且控制乘客是该玩家，把 `vehicleFirstGood` 和 `vehicleLastGood` 都写成载具当前坐标（282–289 行）。

`ServerPlayer.tick`（449–483 行）由实体列表调用，里面没有 `super.tick()`，也不调用 `travel`。

### handleMovePlayer

签名：`public void handleMovePlayer(ServerboundMovePlayerPacket pPacket)`，860 行。顺序：

1. 非法数值则断开（862–863 行）。
2. `wonGame` 为真则整段跳过（866 行）。
3. `tickCount == 0` 时 `resetPosition`（867–868 行）。
4. `awaitingPositionFromClient != null` 时不处理这次位移。超过 20 tick 就再次 `teleport` 到等待坐标（871–875 行）。
5. 乘客只 `absMoveTo` 当前坐标和包里的朝向，并移动玩家区块票（884–886 行）。
6. 非乘客、非睡觉：用包坐标减 `firstGood` 做超速判断，`d10 - getDeltaMovement().lengthSqr()` 超过阈值则 `teleport` 回当前坐标并 return（891–914 行）。睡觉且相对 `firstGood` 的距离平方大于 1 时也 `teleport`，不进入下面的 `move`（896–900 行）。
7. 着地、包报告离地、且相对 `lastGood` 的 Y 大于 0 时调用 `jumpFromGround`（922–924 行）。
8. `move(MoverType.PLAYER, 包坐标 - lastGood)`（918–928 行）。垂直误差绝对值小于 0.5 时，这次错误量的 Y 记为 0（931–932 行）。
9. 错误量平方大于 0.0625，且不是创造、旁观、睡觉、换维，则记为移动错误（938–940 行）。
10. 接受条件在 943 行：`noPhysics`、睡觉，或“不是（移动错误且旧盒无碰撞）且没有新碰撞”。接受时 `absMoveTo` 包坐标（944 行），`doCheckFallDamage`（947 行），`setOnGroundWithKnownMovement(包的 onGround, 接受前坐标到现坐标)`（948 行）。包 Y 高于 `lastGood` 时 `resetFallDistance`（949–950 行）。然后把 `lastGood` 写成 `absMoveTo` 之后的坐标（954–956 行）。这一支不改 `firstGood`。
11. 拒绝时 `teleport(移动前坐标)`，再 `doCheckFallDamage`（957–959 行）。`teleport` 会发纠正包，见下面。

`teleport(double,double,double,float,float)`（982–983 行）转到六参数版（989–1002 行）：记下 `awaitingPositionFromClient`，递增 `awaitingTeleport`，`absMoveTo` 目标，再发 `ClientboundPlayerPositionPacket`。相对集合为空时，包里的坐标就是绝对目标减去 0。

本方法里读到的四次 `teleport(DDDFF)` 在 874、898、913、958 行。`PrisonConnectionMixin` 重定向该方法全部 `teleport(DDDFF)`，以及 `absMoveTo` 的 ordinal 1（`PrisonConnectionMixin.java` 19–46 行）。ordinal 0 是乘客那次 885 行，ordinal 1 是接受落点 944 行。

### handleMoveVehicle

签名：`public void handleMoveVehicle(ServerboundMoveVehiclePacket pPacket)`，402–473 行。根载具不是玩家、控制乘客是该玩家、且载具等于 `lastVehicle` 才继续（407–408 行）。

1. 非法数值则断开（404–405 行）。
2. 相对 `vehicleFirstGood` 的距离平方减去载具 `getDeltaMovement().lengthSqr()` 大于 100，且不是单机主人：发 `ClientboundMoveVehiclePacket(entity)` 并 return（418–426 行）。不更新 `vehicleLastGood`。
3. 记下移动前碰撞 `noCollision(盒收缩 0.0625)`（429 行）。位移用包坐标减 `vehicleLastGood`，Y 再减 `1.0E-6`（430–432 行）。
4. 活体载具在爬梯上时 `resetFallDistance`（434–438 行）。
5. `entity.move(MoverType.PLAYER, 该位移)`（441 行）。方法内没有 `doCheckFallDamage`。`move` 自己会进该载具的 `checkFallDamage`。
6. 垂直剩余误差在 ±0.5 内则错误量 Y 记 0（444–446 行）。剩余平方大于 0.0625 记为移动错误（451–453 行）。
7. 先 `absMoveTo` 包坐标（456 行）。若移动前无碰撞，且（移动错误或移动后发生碰撞），再 `absMoveTo` 回移动前坐标，发 `ClientboundMoveVehiclePacket` 并 return（457–461 行）。这一支不改 `vehicleLastGood`。
8. 接受时更新玩家区块票和移动统计（464–465 行），按剩余 Y、移动前 `verticalCollisionBelow` 和 `entity.isNoGravity()` 写 `clientVehicleIsFloating`（466 行），再把 `vehicleLastGood` 写成载具当前坐标（467–469 行）。不改 `vehicleFirstGood`。

`PrisonConnectionMixin` 重定向本方法里全部 `Entity.absMoveTo(DDDFF)`（48–61 行）。

## 2. 摔落覆盖和客户端纠正

`ServerPlayer.checkFallDamage(double,boolean,BlockState,BlockPos)`（968–969 行）是空方法。因此 `Entity.move` 调到 `ServerPlayer` 的这次覆盖时，不进入 `LivingEntity.checkFallDamage`。

`ServerPlayer.doCheckFallDamage(double,double,double,boolean)`（978–983 行）：未接触未加载区块时 `checkSupportingBlock`，再 `super.checkFallDamage`。父类是 `LivingEntity.checkFallDamage`（287–321 行）：可能更新水中状态、灵魂疾行和落地粒子，317 行调用 `Entity.checkFallDamage`。

玩家移动包的接受和拒绝都显式调用 `doCheckFallDamage`。载具移动包不调用它。

客户端发送：

- `LocalPlayer.tick`（227–240 行）：先 `super.tick()`。乘客发送 `ServerboundMovePlayerPacket.Rot` 和 `ServerboundPlayerInputPacket`；根载具受本地控制时再发 `ServerboundMoveVehiclePacket`。非乘客调用 `sendPosition`。
- `LocalPlayer.sendPosition`（262–308 行）是 private。位移平方大于 `2.0E-4` 的平方或满 20 tick 才发位置；否则只在朝向或着地变化时发 `Rot` 或 `StatusOnly`。

客户端纠正：

- `ClientPacketListener.handleMovePlayer(ClientboundPlayerPositionPacket)`（644–715 行）：按相对标记改旧坐标和速度分量，非相对轴的速度写成 0；`setPos`；`setDeltaMovement`；再发 `ServerboundAcceptTeleportationPacket` 和一次 `PosRot`。
- `ClientPacketListener.handleMoveVehicle(ClientboundMoveVehiclePacket)`（1958–1964 行）：根载具不是本地玩家且 `isControlledByLocalInstance` 时 `absMoveTo` 包坐标，并回发 `ServerboundMoveVehiclePacket`。

本模组已挂上的入口：

- `LocalPlayerPrisonMixin`：`sendPosition` 开头、乘客输入包 `NEW` 之前、`LocalPlayer.tick` 返回。三处都调用 `PrisonClientState.holdLocal`。
- `ClientPlayPrisonMixin`：`handleMovePlayer(ClientboundPlayerPositionPacket)` 开头，只调用 `PrisonClientState.noteServerTeleport`。注释写明不取消、不改包。
- 没有 mixin 注入客户端 `handleMoveVehicle`。
- `PrisonConnectionMixin` 只包住服务端纠正和封包落点，见第 1 节。

`PrisonClientState.holdLocal` 会把被困本地玩家速度写成 `Vec3.ZERO`（`PrisonClientState.java` 124 行）。这是禁锢路径，不是领域运动。

## 3. EntityMoveMixin 与 DomainMotion

`xueximod.mixins.json` 没有顶层 `priority`。`EntityMoveMixin` 的 `@Mixin(Entity.class)` 也没有 `priority` 参数。json 的 `injectors.defaultRequire` 为 1。

```14:24:src/main/java/com/bslx/XueXiMod/mixin/EntityMoveMixin.java
@Mixin(Entity.class)
public class EntityMoveMixin {
    @ModifyVariable(method = "move", at = @At("HEAD"), argsOnly = true)
    private Vec3 xuexiDomainClip(Vec3 movement) {
        return DomainMotion.clip((Entity) (Object) this, movement);
    }

    @Inject(method = "move", at = @At("RETURN"))
    private void xuexiDomainFinish(MoverType moverType, Vec3 movement, CallbackInfo callback) {
        DomainMotion.finish((Entity) (Object) this);
    }
}
```

`DomainMotion` 的公开方法：

- `public static Vec3 clip(Entity mover, Vec3 movement)`，20–48 行。乘客、旁观、`noPhysics`、空向量、长度平方不超过 `1.0E-8`、没有相关领域时返回原向量。`DomainBoundary.OPEN`、整组放行、盒子放不下或尚未完全包含时跳过该领域。完全包含后 `clipInside`，并把 `position + clipped` 放入 `ALLOWED`。
- `public static void finish(Entity mover)`，51–74 行。取出并删除 `ALLOWED`。相关领域里仍有未完全包含的封闭领域时，`setPos` 到记下的点。
- `public static void forget(Entity mover)`，76–80 行。只从 `ALLOWED` 删除。

私有方法：`groupPermitted` 82–92 行，`memberPermitted` 94–96 行，`union` 98–104 行，`relevant` 106–121 行。客户端走 `DomainClientBridge.targets`；服务端收集同世界且 `active` 的 `DomainService.active()`。

`clip` 的返回值就是随后 `move` 使用的位移参数。`finish` 只 `setPos`，不写 `deltaMovement`。

## 4. 现有网络和客户端运动快照

`ModNetwork.CHANNEL` 协议字符串是 `"2"`（`ModNetwork.java` 18–25 行）。`sendToPlayer(ServerPlayer, Object)` 用 `PacketDistributor.PLAYER`（31–33 行）。`register` 依次登记 0 到 17，其中 8 是 `DomainSyncPacket.register`（44 行）。该登记没有 `NetworkDirection`。

`DomainSyncPacket` 含 `instanceId`、`revision`、盒子、`motionKind`、抬升标记、吸引/拉/环绕/上升/行进速度、本体半径，以及 `controlledRoots` 的 UUID 列表（25–50、113–142 行）。`broadcast` 发给该维度每个 `ServerPlayer`，不是只发给受控者或驾驶者（91–98 行）。`handle` 只在客户端调用 `DomainSightStore.accept`（195–197 行）。

`DomainInstance.revision` 是 `private final int revision = 1`（30 行）。本类没有第二次赋值。包里的 revision 来自 `domain.revision()`（187 行）。根列表变化走 `replacePublishedRoots`（287–301 行），不改 revision。

客户端 `DomainSightStore.accept` 调用 `DomainMotionPreview.capture`（18–19 行）。`capture` 把 `MotionFrame` 和根 UUID 放进两张表（17–28 行）。全仓 Java 里没有其他调用读取 `DomainMotionPreview.frame` 或 `controlledRoots`。没有类把这张快照写成 `LocalPlayer` 或载具的 `deltaMovement`。

`ModNetwork.register` 里没有另一个消息以实例 epoch 携带临时运动向量。`ChargeGate.epoch` 出现在施法路径，不在 `DomainSyncPacket` 的字段里。

## 5. 物品、矿车，以及没调用 move 时的尾部

`ItemEntity.tick`（108–158 行）：`onEntityItemUpdate` 返回真则立刻 return。否则 `super.tick()`，再按流体或重力改速度。143 行的条件是：未着地，或水平速度平方大于 `1.0E-5`，或 `(tickCount + id) % 4 == 0`。三个都不成立时，这一拍不调用 `move`。着地且几乎没有水平速度的物品因此不是每拍都 `move`。跳过 `move` 之后，方法仍继续合并、增加 age、流体推动和过期（160–189 行）。本模组没有 `ItemEntity.tick` 的 mixin。

`AbstractMinecart.tick` 服务端（318–341 行）先可能给 Y 加上 `-0.005` 或 `-0.04`。在轨调用 `moveAlongTrack`，否则 `comeOffTrack`。之后仍执行 `checkInsideBlocks`、朝向、推动和流体（343–390 行），这些不依赖前面是否进入 `move`。

`moveAlongTrack`（432–591 行）：

- 上坡时先把局部 Y 加 1，并给水平速度加减坡度（454–470 行）。
- `setPos` 到轨道投影（527 行），发生在 `move` 之前。
- `moveMinecartOnRail`（928–933 行）调用 `move(SELF, Vec3(夹紧后的 X, 0, 夹紧后的 Z))`。传入的 Y 是 `0`。
- `move` 之后，坡端再用 `setPos` 加出口的 Y（529–533 行）。`applyNaturalSlowdown` 把速度乘成 `(水平系数, 0, 水平系数)`（601–609 行）。轨道高度再 `setPos` 一次 Y（536–545 行）。

`comeOffTrack`（410–428 行）夹紧水平速度，着地时整段乘 `0.5`，空中 Y 超过垂直上限时改 Y，然后 `move(SELF, delta)`。离地时再把 `move` 之后的速度乘 `getDragAir()`。这里的 `move` 带有 Y。

这一拍没有 `move` 时，本地仍能到达的尾部：

- `LivingEntity.tick` 在 `ForgeHooks.onLivingTick` 未取消时调用 `aiStep`（2399–2441 行）。`onLivingTick` 只投递 `LivingTickEvent`（`ForgeHooks.java` 264–266 行）。`WetnessLivingMixin` 在 `aiStep` 返回处注入；`travel` 因 `isControlledByLocalInstance` 为假而没进 `move` 时，这个返回仍会执行。
- `Player.tick` 在 `super.tick()` 之后投递 `PlayerTickEvent.END`（245、289 行）。服务端玩家的这次 `Player.tick` 来自 `doTick`，位于 `absMoveTo(firstGood)` 之前。`ServerPlayer.tick` 本身不投递它。
- `TickEvent` 还有 `ServerTickEvent`、`LevelTickEvent`、`ClientTickEvent`（`TickEvent.java` 37–105 行）。没有物品或矿车专用的 tick 类。`ServerTickEvent.END` 在 `connection.tick` 之后，晚于上面的 `absMoveTo(firstGood)`。
- `EntityMoveMixin` 只在 `Entity.move` 被调用时进入。

## 6. isNoGravity 与现有钩子

`Entity.isNoGravity()`（1161–1162 行）只返回 `entityData.get(DATA_NO_GRAVITY)`。`setNoGravity`（1165–1166 行）只 `entityData.set`。数据在 211 行定义，256 行初始为 false。这次没有读到 `ServerPlayer` 或 `LivingEntity` 覆盖该方法。

本模组 Java 里没有 mixin 注入 `isNoGravity` 或 `setNoGravity`。因此现有 mixin 不会在某一拍改这个返回值，也不会借这个方法避开 `DATA_NO_GRAVITY`。

已有移动钩子的实际落点：

- `EntityMoveMixin` 改 `move` 的位移参数，并在返回后可能 `setPos`。
- `WetnessLivingMixin` 在 `LivingEntity.travel` 开头运行。`travel` 内部另行调用 `isNoGravity()`，这个 mixin 不替换那次返回。
- `WetnessFlyingMixin`、`WetnessAllayMixin` 在各自 `travel` 开头。`WetnessVexMixin` 改传给 `Monster.move` 的向量。`WetnessDragonMixin` 改 `aiStep` 里的 `move`。
- 物品、船、矿车读取 `isNoGravity()` 的位置在上一份事实里。它们没有对应的重力返回 mixin。

`setNoGravity(true)` 会写同步数据。现有钩子里没有一条在不调用它的情况下改 `isNoGravity` 的返回。

## 1. 本批写速度的入口和记录

阶段：`ReleaseBaseEvents.onServerTick` 只在 `TickEvent.Phase.END` 调用 `DomainService.tick`（`ReleaseBaseEvents.java` 173–181 行）。`MinecraftServer.tickServer` 先 `onPreServerTick`（842 行），再 `tickChildren`（844 行），最后 `onPostServerTick`（865 行）。`tickChildren` 里先逐世界 `serverlevel.tick`（923 行），再 `connection.tick`（937 行），再 `playerList.tick`（939 行）。`PlayerList.tick` 只广播延迟（512–516 行），不改位置。`ServerLevel.tick` 在 326–352 行遍历实体：非乘客走 `tickNonPassenger` → `entity.tick()`（694–703 行）；乘客走 `rideTick`（712–723 行）。因此本批写速度发生在该拍实体 `tick` 之后。

`DomainService.tick` 先按寿命或主人缺失 `closeAt`（256–280 行），再 `VolumeMotionRuntime.tick`（286 行）。水势耗尽则在 `processHost` 重写速度之前 `closeInstance`（`VolumeMotionRuntime.java` 272–275 行）。

写速度的最小入口都在 `VolumeMotionRuntime`：

| 入口 | 行 | 做什么 | 记到哪里 |
| --- | --- | --- | --- |
| `orbit` → `writeOwned` | 544；1031–1036 | `setDeltaMovement` 三个分量，并 `hasImpulse = true` | 该旋流名册的 `writtenMotion` |

| `liftBubble` | 584–588 | 仅当当前 Y 小于上升速度时改 Y，保留当时的 X/Z | 静态 `BUBBLE_ACTOR`：实体 UUID → 气泡实例 UUID；`BUBBLE_RISE`：实体 UUID → 那个上升值 |
| `revertMotion` | 1040–1055 | 取出记录后，分量和记录相差不超过 `1.0E-4` 才把该分量写成 0 | 取出即从 `writtenMotion` 删除 |
| `clearBubbleRise` | 610–621 | 只比较 Y。相等才把 Y 写成 0，X/Z 原样写回 | 两个静态表都删除该实体 |

`writeOwned` 在名册为 null 时仍写速度，但不记记录（1035 行）。`pull` 用 `ReleaseMotionLedger.find(host)`。入卷前的外围目标也会走这里。`onClose` 只对 `roots(instanceId)` 调用 `revertMotion`（96–101 行）。`claimRoot` 在 `acquire` 成功时才执行（479–481 行），`pull` 不调用它。`releaseInstance` 只清根集合里的 `writtenMotion`（166–177 行）。名册丢弃时整表 `clear`（56–60 行），不改实体速度。

名册按 `releaseGroup + ":" + declarationSlot` 一份（65–66 行），同一声明的分体共用。`controlledBy` 是实体 UUID → 实例 UUID。`rootsByInstance` 是实例 UUID → 根 UUID 集合。`writtenMotion` 的键只有实体 UUID，没有实例 UUID；同一名册里后写的记录覆盖先写的。气泡表是进程内静态映射，一个实体只留一个气泡实例。

离开吸引范围时，`steerGroup` 对当前根调用 `revertMotion`，再 `releaseControl`（377–381 行）。`releaseMissing` 对名册里已控实体做同样的撤销（638–646 行）。这两处能看到记录，不依赖根集合。关闭路径不遍历非根的 `writtenMotion`。

## 2. 原版移位、旅行和击退

`Entity.setDeltaMovement(Vec3)` 只给字段 `deltaMovement` 赋值（3524–3526 行）。`setDeltaMovement(double,double,double)` 转成 Vec3（3532–3534 行）。`addDeltaMovement` 是当前向量相加后再赋值（3528–3530 行）。这三处都不写来源，也不改 `hurtMarked`。

`Entity.push(double,double,double)` 用 `addDeltaMovement`，然后 `hasImpulse = true`（1552–1555 行）。`markHurt` 只把 `hurtMarked` 设为 true（1560–1562 行）。`Entity.hurt` 调用 `markHurt`（1567–1572 行）。

`LivingEntity.knockback(double,double,double)`（1484–1496 行）：先 `ForgeHooks.onLivingKnockBack`，取消则返回。强度再乘 `1 - knockback resistance`。然后 `setDeltaMovement(vec3.x / 2 - 击退水平, 着地时 min(0.4, vec3.y / 2 + strength) 否则保留 vec3.y, vec3.z / 2 - 击退水平)`，并 `hasImpulse = true`。参数里没有来源实体或术式 id。

`LivingEntity.aiStep` 在 2732 行进入 `travel`。若控制乘客是活着的 `Player`，走 `travelRidden`（2743–2747 行），否则 `travel(vec3)`（2751 行）。`travelRidden` 在本机控制时再调 `travel`，否则把速度设为 `Vec3.ZERO`（2290–2299 行）。

`LivingEntity.travel`（2150–2284 行）整段物理包在 `isControlledByLocalInstance()` 里。该方法（3282–3288 行）：控制乘客是 `Player` 时返回 `player.isLocalPlayer()`，否则返回 `isEffectiveAi()`，即 `!level.isClientSide`（3294–3296 行）。

空气/地面分支的实际顺序（2261–2283 行）：

1. 水平摩擦系数：着地用方块摩擦乘 `0.91F`，离地用 `0.91F`。
2. `handleRelativeFrictionAndCalculateMovement`：`moveRelative`，爬梯处理，然后 `move(MoverType.SELF, getDeltaMovement())`（2325–2328 行）。
3. 飘浮药水改 Y；否则在未 `isNoGravity()` 时 `d2 -= d0`。`d0` 先写成字面量 `0.08D`，随即被 `ForgeMod.ENTITY_GRAVITY` 的当前值覆盖（2152–2160、2275–2276 行）。该属性的注册默认值这次未读。
4. 未丢弃摩擦时 `setDeltaMovement(x * f3, y * 0.98F, z * f3)`。

水中分支（2163–2196 行）：`moveRelative`，`move(SELF, delta)`，再按水平系数和 `0.8F` 乘速度，然后 `getFluidFallingAdjustedMovement`。该方法在未无重力且未冲刺时把 Y 减去 `gravity / 16`（2337–2346 行）。熔岩分支在 `move` 之后按系数缩放，未无重力时再 `add(0, -d0/4, 0)`（2201–2214 行）。鞘翅分支先改向量再 `move`，然后乘 `0.99/0.98/0.99`（2221–2247 行）。

`Entity.move(MoverType, Vec3)`（654 行）接收的是这一次位移，不是一份带来源的速度账。`noPhysics` 时直接 `setPos`（655–656 行）。否则 `collide` 裁剪位移（674 行），再 `setPos`（684 行），`setOnGroundWithKnownMovement`（700 行），`checkFallDamage`（703 行）。水平撞上时把 `deltaMovement` 被挡的那一轴写成 0（707–709 行）。最后用 `getBlockSpeedFactor()` 乘当前速度的 X/Z（761–762 行）。`collide` 是 private（934 行）。公开的静态裁剪是 `Entity.collideBoundingBox(Entity, Vec3, AABB, Level, List<VoxelShape>)`（961 行）。

`checkFallDamage`（1177–1189 行）：着地且 `fallDistance > 0` 时调用方块 `fallOn` 并 `resetFallDistance`；未着地且这次 Y 小于 0 时 `fallDistance -= (float)pY`。`LivingEntity.causeFallDamage`（1587–1599 行）经 `ForgeHooks.onLivingFall` 后调用 `super`，再按 `calculateFallDamage` 扣血。`Entity.causeFallDamage` 对坠落免疫类型直接返回；载具会把同一次调用转给乘客（1197–1207 行）。

因此：把一段位移直接交给 `move`，碰撞裁的是这次传入的向量；持久 `deltaMovement` 仍是原来的字段，只在撞墙、方块速度系数这些后续语句里被改。`move` 同时会改位置、着地、摔落距离和可能清掉被挡轴的速度。本地源码里没有第二个“只裁剪贡献、不碰持久速度和摔落”的方法。

## 3. 玩家、物品、船、矿车、飞行生物

共同入口：都是 `Entity`。服务端非乘客最终到各自的 `tick()`。`EntityMoveMixin` 挂在 `Entity.move` 的参数和返回（`EntityMoveMixin.java` 16–23 行），所以这些 `move` 都会进 `DomainMotion.clip`。

不同入口：

- 玩家：`Player.travel`（1489 行）先可能按游泳改 Y，飞行时记下旧 Y，调用 `super.travel`，再把 Y 写成 `旧Y * 0.6` 并 `resetFallDistance`（1502–1510 行）。不飞行则只 `super.travel`。服务器移动包 `handleMovePlayer`（860 行）用 `move(MoverType.PLAYER, 位移)`（928 行），接受后 `absMoveTo`（944 行），再 `doCheckFallDamage` 和 `setOnGroundWithKnownMovement`（947–948 行）。这个包在 `connection.tick` 期间处理，位于世界实体 tick 之后、`ServerTickEvent.END` 之前。
- 乘客：`Entity.rideTick` 先 `setDeltaMovement(Vec3.ZERO)`，再 `tick()`，再由载具 `positionRider`（2027–2032 行）。
- 物品：`ItemEntity.tick`（108 行）不走 `LivingEntity.travel`。未浸没且未 `isNoGravity` 时 Y 加字面量 `-0.04`（130–131 行），然后 `move(SELF, delta)`（144 行），再乘 `0.98` 或着地摩擦（145–151 行）。
- 船：`Boat.tick`（284 行）在 `isControlledByLocalInstance()` 时 `floatBoat` 再 `move(SELF, delta)`（307–318 行），否则 `setDeltaMovement(Vec3.ZERO)`（319–320 行）。`floatBoat` 默认重力字面量 `-0.04`，`isNoGravity` 时用 0（608–610、638–639 行）。玩家乘坐时，控制乘客是玩家，服务端 `isLocalPlayer()` 为 false，因此走清零分支。车辆包 `handleMoveVehicle`（402 行）对根载具 `move(MoverType.PLAYER, 位移)` 再 `absMoveTo`（441、456 行）。
- 矿车：`AbstractMinecart.tick` 服务端分支不看 `isControlledByLocalInstance`。未无重力时加水中 `-0.005` 或 `-0.04`（319–321 行）。离轨 `comeOffTrack` 里 `move(SELF, delta)`（425 行）。
- 飞行生物：`FlyingMob.travel`（16 行）不调用 `LivingEntity.travel`。水/熔岩里 `move` 后整段缩放；空气里 `moveRelative`、`move`，再按 `0.91F` 或着地摩擦缩放（16–41 行）。`FlyingMob.checkFallDamage` 是空方法（13–14 行）。
- 恼鬼：`Vex.tick` 在 `super.tick()` 期间把 `noPhysics` 设为 true，之后 `setNoGravity(true)`（80–84 行）。`noPhysics` 的 `move` 不碰撞。`Vex.move` 仍调用 `super.move`（72–74 行）。
- 末影龙：`EnderDragon.aiStep`（177 行）自己 `move` 和 `setDeltaMovement`（271、287、289、294 行），不经过 `LivingEntity.travel`。

`setNoGravity` 只写实体数据 `DATA_NO_GRAVITY`（1165–1167 行）。`travel`、物品、船、矿车各自读取 `isNoGravity()`，读到 true 时跳过自己的那次重力加法。

`hurtMarked`：`ServerEntity` 在发送循环末尾若为 true，广播 `ClientboundSetEntityMotionPacket` 后清掉（202–204 行）。`setDeltaMovement` 本身不置这个标记。`hasImpulse` 在同文件 198 行被清掉。

本模组已有入口：

- `TechniqueMotion.tick(TechniqueHitEntity, ServerLevel)` 只服务命中实体，不覆盖旋流根。
- `DomainMotion.clip(Entity, Vec3)` 在 `move` 前改位移。乘客、旁观、`noPhysics`、近零位移直接返回原向量（20–25 行）。`DomainBoundary.OPEN` 的领域也跳过（36 行）。`DomainDefinition.vortex` 和 `bubble` 登记的是 `OPEN`（210、224 行）。`finish` 只在封闭领域里把穿出者 `setPos` 回允许点（51–73 行）。
- `WetnessLivingMixin` 注入 `LivingEntity.travel` 开头。`WetnessFlyingMixin` 注入 `FlyingMob.travel` 开头。`WetnessVexMixin` 改 `Vex.move` 传给父类 `Monster.move` 的向量。`WetnessDragonMixin` 的 `@Redirect` 要求命中 `EnderDragon.aiStep` 里两次 `move`。`WetnessAllayMixin` 注入 `Allay.travel` 开头；`Allay.travel` 方法体这次未读。物品、船、矿车没有对应的 travel 意图 mixin。

## 4. 继续用速度时，来源能不能分开

`deltaMovement` 是一个 `Vec3` 字段。`setDeltaMovement`、`addDeltaMovement`、`push`、`knockback`、`travel` 末尾的 `setDeltaMovement` 都只改这个字段。签名里没有贡献者、实例 UUID 或“这一份是重力/击退/术式”的标记。

击退用当前 X/Z 的一半再叠加自己的量，Y 在着地时也混进强度。旅行随后用系数乘整个向量，或先 `move` 再取 `getDeltaMovement()` 继续乘。撞墙还会把某一轴写成 0。这些结果仍是一个三元组。

本地这些方法没有保留加法前的各来源。从一个旅行之后的总速度，不能唯一拆回旋流写下的分量、重力、摩擦和击退。相等比较只在当前值仍等于记录值时成立；这次读到的乘法和加法会改变该值。

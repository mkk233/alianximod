# 弹射类别与潮湿下压（事实补充）

只补这两点。不改原现状报告，不做方案结论。

## 1. Deflection 实际接受的弹体

类型门在 `ArrowSupport`（`src/main/java/com/bslx/XueXiMod/shu/technique/release/deflection/projectile/ArrowSupport.java` 6–20 行）。`supportsType` 只在运行类恰好是 `Arrow` 或 `SpectralArrow` 时为真。注释写明：药箭的类仍是 `Arrow`，所以带药水的普通箭进门；三叉戟以及任何重写了命中的 `AbstractArrow` 子类不进。

唯一弹体 mixin 是 `ArrowDeflectionMixin`，目标类 `AbstractArrow`（`src/main/resources/xueximod.mixins.json` 只列这一处箭 mixin）。进入报价前都再查 `ArrowSupport.supported`：

- `tick` 头，67–68 行，只给支持的箭刷出口。
- `tick` 头后段，87–89 行，只给支持的箭开本拍状态。
- `findHitEntity` 之前，98–100 行：客户端、不支持、无碰撞或已移除直接返回，不调用 `ArrowFlight.consider`。

因此 `ThrownTrident` 虽是 `AbstractArrow`，类不相等，不会进 `consider`。火球、雪球、喷溅/滞留药水、末影珍珠、经验瓶、焰火、羊驼唾液、潜影贝导弹、鱼钩在 `deflection` 包和 mixin 里没有类型分支，也没有第二处调用 `ArrowFlight` 或 `DeflectionEconomy.quote`。全仓 `ArrowFlight` / `tryAcquire` 的弹体调用只来自这支箭 mixin。

成本入口只在支持的箭上：

1. `ArrowFlight.consider` 62–65 行再次拒绝不支持、无碰撞、已移除。
2. `direct` 由 `quote` 174–181 行算出：`ArrowDamageFreeze.freeze`（`ArrowDamageFreeze.java` 14–33 行）是 `ceil(clamp(速度 × getBaseDamage()))`，暴击再加一次 `nextInt(base/2+2)`，然后加领域光环浮点。不是按弹种写死的常数。光灵箭走同一函数，没有单独公式。药水效果不进入 `freeze`。
3. 非暴击且 `ceil` 基数 ≤0 且光环 ≤0 时，`quote` 返回 0（178–179 行）。`consider` 133–138 行见到 `direct == 0` 直接返回，不调用 `tryAcquire`。这是“已进门但没有直接伤害”的箭，不产生 `fullCost`。
4. 有直接伤害才到 `attempt` 213–214 行：`DeflectionService.tryAcquire(..., direct, fullCount, false, shooterProfile)`。`false` 表示不是近战。`DeflectionEconomy.quote` 28–49 行因此走箭支：`fullCost = direct * profile.arrowCostRatio()`。档位是射箭者的 `WetnessTiers`（`ArrowFlight.shooterProfile` 185–190 行）。

近战是另一条，不是弹体：`MeleeDeflection` 209–210 行把 `direct` 传 0、`isMelee` 传 true，费用用攻击者湿度的 `meleeCost`。宿主 `eligible` 默认接受（`DeflectionHost` 48–49 行）；水牢收紧为被困者本人（`PrisonDeflectionHost` 58–62 行）。宿主不按火球或雪球分类。

`DeflectionFlightEvents.onJoin` 29–30 行对任何 `AbstractArrow` 调用 `resumeLoaded`，但 115–116 行要求已有捕获标记。不能凭空给三叉戟报价。

结论：有 `direct` / `fullCost` 的只有类恰好为 `Arrow` 或 `SpectralArrow`、且冻结后的直接伤害大于 0 的箭。其余弹射物没有成本入口，也没有“明确支持但费用为 0”的分支。

## 2. 潮湿下压实际写速度的位置

`WetPressure` 五个公开方法体都是空的（`payload/WetPressure.java` 9–30 行）。类注释写明旧重压已停用，命中后不再给缓慢或下压，并且不改深海领域自己的减速、施湿和耗氧。

仍会调用这些空方法，所以不会写出速度：

- 生成：`TechniqueHitSpec` 439–441 行，仅当 `pressureWetnessMinimum() > 0`。失败或未发布时 `clear`（434、445、454 行）。
- 命中后：`TechniqueHitSettle.afterDamage` 181、190、262、306 行。
- 批次汇总后：`ReleaseBatch.afterFlushed` 466 行，以及同方法后两处同类调用。
- `HostGroupContext` 223 行 `clear`。

深海领域包内没有 `setDeltaMovement`。深压减速是药水，不是下压速度。

现在真正按潮湿改竖直速度的是 `WetnessFlight`，与 `WetPressure` 不是同一条链。

资格在 `clampDescent`（175–204 行）：服务端、非恼鬼、非末影龙、蝙蝠非栖息、活着、不在豁免名单、不是乘客、不在地上、不在真实流体（`actualFluid` 70–71 行：`isInWater`、`isInLava` 或 `isInFluidType`）。湿度档 `< 3` 不改。3 档把竖直速度压到不超过 `-0.08`，4 档不超过 `-0.30`（`limitedVertical` 34–46 行）。只在当前竖直速度比这个上限更靠上时替换 `deltaMovement` 的 Y，水平不动。不改摔伤，不设 `hurtMarked`。

调用时序：

- `WetnessLivingMixin` 在 `LivingEntity.travel` 头（12–17 行）调用 `beforeTravel`。注释写的是移动控制之后、本拍 `travel` 使用速度之前。
- `FlyingMob.travel` 和 `Allay.travel` 不走 `LivingEntity.travel`，各自在自己的 `travel` 头调用（`WetnessFlyingMixin` 16–17 行，`WetnessAllayMixin` 16–17 行）。
- 恼鬼不走 `clampDescent`。`WetnessVexMixin` 在 `Vex.move` 调用父类 `move` 时改位移向量（15–21 行），`adjustVexMove` 只对 `MoverType.SELF` 加上 `extraDown`（90–106 行），方块会裁掉这段追加。
- 末影龙：`aiStep` 头 `beginDragonStep`（41–43 行）；两次 `move` 前 `adjustDragonMove` 只记下追加量（46–52 行）；第一处 `checkWalls` 前 `correctDragonDescent` 用 `setPos` 下移龙和部件（55–62 行，`WetnessFlight` 132–167 行）。默认豁免名单含 `minecraft:ender_dragon`（`WetnessFlightExempt` 13–14 行），豁免时 `correctDragonDescent` 146–147 行直接返回，不写位置。
- `WetnessWitherMixin` 只让凋灵能加上潮湿效果，不写速度。

没有一个速度贡献列表或统一仲裁函数。潮湿下压是在 `travel` 头替换 Y。命中载荷的上升是另一次加法：`HitPayloads.apply` 74–76 行、`FlowSuccessPayload` 107–109 行，都是 `add(0, liftStrength, 0)` 并设 `hurtMarked`，发生在命中结算，不在 `travel` 头。场地牵引是再一次加法（`FieldZones` 323–324 行，竖直只取 0.2）。这三处互不调用。上述 mixin 都没有写 `priority`。

因此气泡上升若要和潮湿下压相遇，现有代码里没有已排序的贡献入口。能看到的事实只有：3/4 档且本拍仍满足下降资格时，下一次 `travel` 头会把当时的 Y 压到 `-0.08` 或 `-0.30`；人在真实流体里则 `clampDescent` 不改 Y。`WetPressure` 不参与这次比较。

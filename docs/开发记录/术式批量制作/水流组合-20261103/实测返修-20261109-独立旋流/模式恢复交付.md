# 模式恢复交付

固定 CLI 的 `--mode` 只有 `plan` 和 `ask`。ask 的说明是只读问答，没有可写取值，也没有同会话的模式切换或清除参数。写模式继续不传 `--mode`。持久化 Ask 不能靠省略 `--mode` 解开，也不使用隐藏的 `--new-session-id`。

因此恢复入口是显式的同 task Cursor 会话重建：主会话同时给出 `Resume`、`-WriteMode`、`-RecoverPersistentAsk` 和 `-ResumeReason`。启动器用既有 `create-chat` 读取真实 UUID，再 `--resume` 这个新会话。旧 attempt、旧会话来源和 batchId 额度都保留。本次没有执行 source-owner 的真实恢复。

## 新增参数

`-RecoverPersistentAsk` 只和 `Resume -WriteMode` 一起使用，并且不能带 `-UseQuotaFallback` 或 `-AccountQuotaEvidence`。普通 Start、普通 Resume 和只读 Resume 的行为不变，也不会自动新建会话。

调用前必须同时满足：

- 当前 provider 仍是 Cursor，没有 Grok 会话或已用过的额度切换。
- TaskFile 的 `writePaths` 非空。
- 最新 attempt 是已记录的持久化 Ask 阻塞：provider 为 Cursor，`lifecycle=reported`，`reportStatus=valid`，`workStatus=blocked`，`mode=write`，`readOnly=false`，回执 `writesSettled=true`，`changedFiles` 为空，可见文本含确切句子 `Ask mode is still active`。
- 该 attempt 的进程戳显示已经收束。
- 当前 TaskFile 的 `stage`、`writePaths`、`dependencies` 与该 attempt 一致。`inputVersion` 可以是主会话当前批准的版本，旧值和新值都会记下。

审批拒绝、协议异常、取消、额度失败、活着的启动器锁、未收束进程戳，都直接拒绝，并且不调用 `create-chat`。`create-chat` 失败或新进程没能启动时，当前 `cursorSessionId` 保持原值。

成功后，`task.json` 的当前 Cursor 会话改为新 UUID，`cursorSessionRecoveries` 追加旧 UUID、新 UUID、原因、父 attempt 和输入版本。新 attempt 写入 `session-recovery.json`。之后的普通 Resume 只续这个新会话。

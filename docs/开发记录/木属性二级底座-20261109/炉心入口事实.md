## 2. SELF_STATUS 与花谱

`ReleaseKind.SELF_STATUS` 的注释只表示不生成命中体，链上角色另报。真正提交时却只消费炉心动作。现有调用者是升温、燃烧、冷却。协同规则也把种类标成 `SELF_STATUS`（`CooperativeContent` 106–107 行），角色却是 `RULE_COOPERATIVE`，没有实现 `selfStatus()`。它能离开这段炉心提交，是因为协同编译器先接走；一旦落到 603 行，空的 `selfStatus()` 会被当成炉心拒绝。

花谱设计是玩家自身状态、30 秒、时间到了不再给新的插枝资格；已有枝印和落英按自身时限结束。六种来源如何同时携带仍是设计待定。按现在的药水模型，同一种效果同时只有一份实例，一份时长、一个整数等级。炉心把这个整数收成 0 或 1，并且每次规范化都改回无限时长。六份独立的 30 秒来源放不进这一份 `furnace_core`。不同效果类型可以同时挂在玩家身上，那是原版效果表的能力，不是炉心档位的能力。热量、过载、降档禁止、治疗削减、抗性失效和冷却蒸汽都只描述炉心，不能当成花谱规则。

已经能沿用的是施法骨架：种类不生成命中体、混链拒绝、松开再按、预检后扣款、失败退款且不进冷却、`ModMobEffects` 的延迟注册，以及原版对有限时长效果的同步和到期。不能直接复用的是炉心效果类、存档、转换表、事件和 `SelfStatusCommit` 的动作开关。

## 3. 不新增花谱术式时的最小改动候选

只在 `ModMobEffects` 再登记一个独立效果，不会改变炉心行为，也还没有施法入口。以后的术式可以自己 `addEffect`，时长用 600 tick 这类有限值。这样做复用的是注册表和原版效果生命周期，不是炉心状态机。牛奶、死亡、换维都按原版走，除非另写事件。

若希望以后的术式走同一条「预检、扣款、失败不冷却」提交，就要改消费炉心类型的接口，而不是改热量公式。候选是 `SelfStatusCast`、`SelfStatusCommit.commit`、`SelfStatusDefinition` 的三式登记，以及 `SkillUsePacket` 603–611 行：这里凡是种类为 `SELF_STATUS` 且没被协同路由器接走的段，都会送进炉心提交。`ReleaseDefinition.selfStatus()` 现在的默认值是空，但返回类型已经是炉心动作，调用方无法表达另一种状态。

不建议把花谱参数加进 `FurnaceService`、`FurnaceMath` 或 `FurnaceMobEffect`。那会让无限时长、两档和热量爬坡碰到木系。

回归风险集中在三式已经依赖的顺序：预览失败不扣款；扣款后转换失败必退款；拒绝和魔力不足都不写槽位冷却；只有主动冷却成功才放蒸汽；普通升过载保留热量；升级不重播升温。协同继续占用 `SELF_STATUS` 这个种类，泛化时不能让协同链掉进炉心提交。火伤查询仍应只认炉心快照。

## 1. 资源接口只覆盖活体上的整数

条件查询的读口是 `ResourceStatus`：`ResourceLocation identifier()` 与 `ResourceView read(LivingEntity subject)`。注释写明实现只能读数值、档位和可选时长，不能改实体持久数据。`ResourceView` 是 `record ResourceView(ResourceLocation identifier, int value, int tier, int durationTicks)`，三个数都是 `int`，没有小数份额，也没有地面坐标或来源构成。

```7:10:src/main/java/com/bslx/XueXiMod/shu/technique/release/statusquery/ResourceStatus.java
public interface ResourceStatus {
    ResourceLocation identifier();
    ResourceView read(LivingEntity subject);
}
```

注册表在 `ResourceStatuses`。稳定 ID 只有两个：`xueximod:wetness`，以及 `FireSeedState.IDENTIFIER` 即 `xueximod:fire_seed`。`registerBuiltins()` 在首次查找或 `StatusScan` 时放入潮湿和火种。`register(ResourceStatus provider)` 对同一 ID 再次登记会抛 `IllegalStateException`。仓库内没有调用 `register(ResourceStatus)` 的生产代码，现成登记只有这两项内建。`find` 对空键返回空；`readAll` 要求读出的视图 ID 与提供者 ID 一致，否则丢掉该条。

`StatusQuery.resourceAtLeast(ResourceLocation, int)`、`effectActive` 和 `and` 只做只读命中。未知 ID 不命中，这里不发放、不对齐。比较的是 `view.value() >= lowestInclusive`。

整数落在实体持久数据，键是复合标签 `xueximod_attribute_states`。`AttributeStateData.read(LivingEntity, String)` 缺标签时返回 0；`write` 把小于等于 0 的值删键。查询用的是 `ResourceLocation`，存盘用的是另一个字符串：潮湿 `"wetness"`，火种 `"fire_seed"`。`AttributeStateDefinition` 只持有这个字符串和上限。`AttributeStateService.read/write` 做空对象保护和上下限钳制；`replace`、`clear`、`reconcile` 在客户端直接返回。进世界对齐只接到潮湿：`AttributeStateEvents.onEntityJoin` 调用 `WetnessState.reconcile`。火种不注册药水，不走这套到期。

火种公开入口在 `FireSeedState`：

- `int value(LivingEntity)`
- `Optional<FireSeedSnapshot> preview/consume(LivingEntity, FireCastContext, int requested, double furnaceBonus)`
- `Optional<FireSeedSnapshot> consumePrepared(..., SnapshotReady ready)`
- `int draw(LivingEntity, int spent)`
- `int grant(LivingEntity, FireCastContext, int baseAmount, double productionMultiplier)`
- `void discard(LivingEntity)`、`void retainLivingClone(LivingEntity original, LivingEntity fresh)`

上限 `FireSeedMath.UPPER_BOUND = 100`，每档 10。`value`、预览、扣点和生产都要求服务端主线程；`value` 在客户端或非主线程返回 0。能改账还要求目标存活且 UUID 非空。0 与无资源相同。查询时长用 `UNLIMITED_DURATION = -1`，不借用潮湿的 1000 tick。

因此现有增加、预览、消耗都作用在活体的一份整数余额上。地面对象、方块坐标和“一批资源里的未消费份额”没有对应参数。

## 2. 世界里已有载体，分成会存档的和只活在本进程的

会随世界保存、并按该维度游戏时间到期的生产路径，是分水租约 `WaterPartingSavedData`。存储 ID `xueximod_water_parting`，`get(ServerLevel)` 走 `computeIfAbsent`。`adopt` 记下操作 UUID、`expireGameTime` 和格子；`WaterPartingService.tick` 调用 `observeAndExpire`，游戏时间到达期限就摘掉持有者。类注释写明：停服不把 200 tick 走完；玩家数据和这份存档没有跨文件崩溃原子性。同一格可以挂多个操作 UUID。这是方块租约，不是可部分消耗后再按剩余份额发奖的资源。

同级 `SavedData` 还有静水租约 `StillWaterLease`（`xueximod_still_domain_water`，区块加载时补应用）、水牢未扣湿度票据 `PrisonWetDue`（同一 `prisonId` 保持第一次，扣完才删）、末地非死亡结算的湿度交接 `PrisonWetTransfer`（普通死亡不记，断线丢掉，因为结果已经在即将存档的玩家身上）。它们都是水玩法票据或方块租约。

活体上会存档的燃烧账是另一条生产路径。`BurnCarrier.read/write/clear/copy` 使用 `FireLimits.SAVE_KEY = "xueximod_fire_burn"`。死亡清除；存活克隆才复制。它记录的是已经挂上的燃烧计划，不是地面份额。剑实体有自己的 `addAdditionalSaveData`，保存的是武器状态，不是资源池。

只活在本次服务器进程、用服务器 tick 到期的地面或空间宿主：

- `GroundFireFields`：静态 `CopyOnWriteArrayList`，`open(ServerLevel, FireCastContext, Vec3, double radius, int lifeTicks)`。注释写明不改方块，火场只活在这次进程。到期调用 `FireVisualRelay.closeGround`。没有卸载存档，也没有自然结束转成玩家资源。`GroundFireMath` 只做几何。
- `SurfaceFireHosts`：静态 `HashMap`，默认寿命 100 tick。主人登出或维度卸载时 `close()`。注释写明结束后不再产种，已有燃烧和火种余额不在这里删除。
- `FieldZones`：静态表。`tick` 在寿命到、主人不在、死亡或维度不一致时拆掉。`ReleaseBaseEvents.endCast` 在玩家死亡、登出、换维时 `closeOwned`。
- `DomainService`：静态 `ACTIVE`。同一 `endCast` 会 `closeOwned`。寿命用 `ReleaseInput.hasExpired(nowTick, expiryTick)`，比较的是服务器 tick，不是分水那种游戏时间。

这些宿主能说明“一块地面效果如何出生、每 tick 扫描、到期拆掉、视觉包怎么发”。花瓣份额不能直接挂进去：它们不保存可分次扣除的剩余量，进程结束或换维会拆掉，拆掉时也不向玩家记一笔来源贡献。

灼地去重 `ScorchSeedLedger` 也只活在进程内，不写 NBT。首次键是施法者、共享释放令牌和目标；周期键另算。入账走 `FireSeedProduction.produce`，明确不要把共享释放上下文交给 `FireSeedState.grant`。这是火种产种去重，不是地面资源账。

视觉同步是 `FireVisualPacket`，在 `ModNetwork.register` 里编号 11。它告诉客户端火场或灼地的出生和结束，不回写服务端余额。

## 3. 岁华可以对照的玩家存档、客户端和一次扣款

玩家身上已经有一份持久复合标签。`PlayerShuData` 的键是 `xueximod_shu_data`，`get/save` 读写魔力整数以及术进度。`PlayerConnectionHandler.onPlayerClone` 无论是否死亡，都把 `xueximod_bound_skills`、`xueximod_shu_data`、`xueximod_spell_storage` 抄到新身体。登出时再 `save` 一次。登录和重生用 `ShuSyncPacket` 把等级、使用次数、魔力当前值和上限、已学术发给该玩家。魔力变化时 `MagicPool` 会再次保存并单发这个包。`MagicPool.forget` 只清回蓝计时，不清已存魔力。

炉心是另一份仅玩家使用的标签 `xueximod_furnace_core`。`FurnaceEvents.onClone` 在死亡时清效果、存档和属性修饰；非死亡克隆才 `FurnaceStore.copy` 并按档重建无限药水。登录时 `reconcile` 并重排时钟。热量在服务端标签里，客户端可见的是药水档，不是一份资源构成。

火种若在玩家身上，走的是实体持久数据，不是术数据。`FireSeedLifecycle` 在死亡时 `discard`，只删火种键。死亡克隆不再抄回，并再清一次新身体。末地回主世界的存活克隆和生物转化只补火种这一个整数。类注释写明下界和末地传送仍是同一个玩家对象，所以这份数据留在身上；换维时期没有火种复制逻辑。`FireSeedVisualRelay` 在登录、重生、换维和开始追踪时把当前余额发给观察者，余额变化时发给追踪者和自己。

客户端 `FireSeedFlameClient.accept` 只按余额画火苗。余额档位为 0 就删显示。注释写明不改火种账。通道是 `FireSeedVisualPacket`，编号 12，方向仅服务端到客户端。

## 4. 幂等、批次和来源：现有钩子与候选文件

`FireCastContext` 把生产和消费去重记在对象内的目标 UUID 上，不进全局表，也不存实体。同一对象对同一目标 `grant` 一次、`consume` 一次。`claimEffect(UUID, String)` 另用“目标|效果键”，不写入生产或消费集合。注释写明：新建另一个上下文，即使施法 ID 相同，也是另一本账。`FireSeedGrant.deposit` 和 `FireSeedProduction.produce` 每次都 `new FireCastContext(UUID.randomUUID(), ...)`，所以它们不占用调用方那本账，也不能靠随机上下文把一整批地面物体收成一次奖励。

`grant` 只有 `floor(基数 × 倍率)` 仍大于 0 才 `markProduced`。已经 100 时，正请求的实际增加可以是 0，机会仍然记下。取整结果为 0 则直接返回，不占机会。`SeedMerge.commit` 复用调用方上下文；请求大于 0 就占生产机会，满额增加 0 也占。它把两笔整数加成一个余额，合完不再记得哪一笔来自哪里。

会留下来的一次性标记有两处。`NetherSeedArbiter.grant` 用实体上的 `xueximod_nether_seed_window`：窗口 ID 相同直接返回已处理；入账结果不是 -1 且目标仍存活后才写入。不能行动时返回 -1，调用方不得记下窗口。`PrisonWetDue.keep` 对同一 `prisonId` 保持第一次。两者都是“同一键只成功记一次”，不是“一批里未消费的那一部分到期转换，已消费部分永不再奖”。

地面宿主到期或被登出、卸载拆掉时，现有代码只关闭宿主或视觉。灼地注释明确不删除已有火种。没有“自然凋谢才入账、外力移除不入账、且只入账一次”的标记。终极技来源永不产岁华、分割合并不能洗来源，在火种、燃料拆分和产种合并里也没有对应字段；合并和拆分都会把构成丢掉。

## 5. 火系生命周期和配置怎么接，避免另起一套目录

火种没有自然衰减。余额留到消费、`draw` 或目标死亡。熄火、进水、抗火和牛奶没有清火种的入口。存档、卸载再加载靠实体持久数据；玩家登出没有火种清除逻辑，登录再发显示包。死亡和死亡克隆丢弃。存活换维保留整数。客户端那份余额不参与生产和消耗。

生产公式在 `FireSeedMath.floorProduction`：非有限或乘积小于 1 得到 0，不设最低 1 点，结果再钳到 100。无炉心时 `FireSeedProduction` 仍读 `FurnaceService.seedMultiplier`。固定点数的 `FireSeedGrant.deposit` 用倍率 1.0，并先过 `DamagePermission.allows`。消费请求里 `Integer.MAX_VALUE` 表示当时全部余额，负数不是全部消费；`invested` 取请求与余额的较小值。同一上下文同一目标消费成功后不能再消费。`draw` 不占这次引爆机会，所以分段燃烧可以继续花后来补进的余额。

炉心只服务玩家，普通与过载两档。它改的是产种倍率、显式火伤和承伤，不是第二种资源条。`ResourceStatuses` 不登记炉心。

配置目录按术式稳定 ID，不按资源条。`XueXiMod.commonSetup` 先 `ModNetwork.register`，再 `ModTechniques.registerAll`，记下内置术式，投递 `RegisterXueXiContentEvent`，然后 `BalanceCatalog.sealAfterContent`。封存顺序是补标准键、`ModTechniques.declareSpecialBalances()`、`EnchantmentDefinitions.declareBalance`、`BalanceRegistry.seal`。同一键再次声明会拒绝。外部专项用 `event.registerBalance(TechniqueBalanceSpec)`，失败返回 false，不另建目录。读取是 `BalanceService.number(techniqueId, parameterKey)` 和 `intValue`。世界重启后生效，本版不热重载。指南文首写明配置底座自己的编译已通过、游戏未测、复核额度已用尽；那次编译不能当成木属性玩法已实现或已在游戏里通过。

木属性设计第 8 节写明：现在没有这套玩法的稳定 ID、参数键或代码接入，不编造键名；花谱配比、命中计次和岁华来源不做配置开关。火种相关的 `seedCount` 是 `fire_nether_gloom`、`fire_seed_sow` 等术式自己的专项，替换的是产种基数，不是一条可调的资源上限开关。新术式以后用指南里的 `TechniqueBalanceSpec.builder(稳定ID)` 加 `numberParameter` / `integerParameter`，标准冷却、魔力和伤害倍率不要在专项里再声明一次。本次底座还没有术式 ID，配置目录无从登记。

# 性能记录使用说明

这是默认关闭的服务端观测。它只记录完整 tick 的墙钟和已经列明的业务耗时、次数。它不改变玩法，不缓存查询，不改调度，也不承诺帧数或耗时变好。

命令在服务端注册，权限等级 2。专用服控制台可以直接使用。没有客户端命令界面。

## 命令

- `/shuperf start`：进入待命，目标 1200 个完整 tick。
- `/shuperf start <ticks>`：目标改为 1 到 6000 的整数。超出范围由命令参数直接拒绝。
- `/shuperf stop`：按下面的状态机停止。
- `/shuperf status`：只显示状态、已完成/目标 tick、未完整 tick、最近一次成功导出的目录。不排序，不写盘，也不开始采样。
- `/shuperf export`：仅在已经停止、并且服务器还在运行时，把内存结果写成文件。

未知子命令和非法参数走原版命令错误。

## 状态

`IDLE` 空闲。服务器启动后强制回到这里，旧的内存结果和服务器引用都会清掉。

`ARMED` 待命。`start` 只进入待命，从下一个服务端 tick 的 START 才开始第一个完整 tick。下达命令时那一段残缺 tick 不录，也不算进未完整 tick。

`RECORDING` 正在录完整 tick。

`STOP_PENDING` 已经请求停止，当前这一格如果还开着，会录完它的 END 再停，不会把这一格截断。如果命令落下时并没有打开的 tick，下一个 START 只负责停止，不会再多录一格。

`STOPPED` 已停止。这时可以导出。再次 `start` 会换成新的内存结果，并提示先前结果已经不在内存里；若上次导出过，目录还在磁盘上。待命、录制或等待停止时再次 `start` 会被拒绝，已有数据不动。

没有墙钟定时线程。服务器卡住、tick 不再前进时，不会另行超时。所谓到时，就是录满请求的完整 tick 数。上限 6000，满了就停，不环形覆盖，也不抽样。

`stop` 在待命时立刻取消，并留下 0 个完整 tick 的停止结果，可以导出。导出里的平均值和 P95 写 N/A。

同一次 JVM 里再次进入世界或启动服务器，会丢掉上一次的内存结果，不会继承，也不会在退出时自动写盘。要保留结果，必须在服务器退出前导出。

## 导出

目录固定为：

`<游戏工作目录>/logs/xueximod-performance/<UTC时间戳>-<序号>/`

里面有 `summary.txt` 和 `ticks.csv`。目录名自动生成，文件用创建新文件的方式写入，不会覆盖已有文件。再次导出同一个停止结果会另开一个新目录。没有路径参数。

写文件在服务端命令线程里同步进行，排序也在这时进行，都不算进刚才那段采样。服务器会在导出期间停在这条命令上。测完再导出。这里不保证导出本身毫无卡顿。

写失败时内存结果保留，命令里带回实际错误。玩法状态不改。若目录已经建出来但文件没写完，那个目录可能是空的或不完整，不能把它当成成功导出；成功时 `status` 才会记下该目录。

## 观测 tick

`observed_server_tick_ms` 可以称为观测 MSPT。它是 Forge 服务器 tick 事件从 START（最高优先级）到 END（最低优先级）的墙钟。

它不包括两格 tick 之间的休眠或等待，也不包括这些事件钩子外面的工作。它不是原版完整 MSPT，也不是纯 CPU 时间。这一段里面的 GC、线程抢占和采样自身的开销都算在里面。同一优先级上别的监听器谁先谁后并不保证，所以不能把这个窗口理解成已经包住所有同优先级监听器。

报表里的平均值、P95 和峰值都只针对已经完成的观测 tick。P95 用排序副本的 nearest-rank：下标是 `ceil(0.95*N)-1`，整数实现是 `(95*N+99)/100-1`。N 为 0 时写 N/A。业务调用只有次数、总纳秒、平均纳秒和单次峰值，没有调用耗时 P95。不要把 tick 的 P95 当成某个方法的 P95。

`ticks.csv` 最多 6000 行，按 tick 序号排列。每行有 tick 纳秒、观测毫秒、目标查询次数、实体查询次数、二者之和、两类候选数和候选合计、攻击体更新次数、剑更新次数。

## 读数时不要加总

所有业务耗时都是 inclusive。它们可以嵌套，同一种也可以重入，累计可以大于墙钟。不能相加当总 CPU，不能画成互斥比例，也不能从观测 tick 里逐项减掉。

每 tick 的查询次数只等于目标查询次数加实体查询次数。这两类次数互斥。剑的 owned 全实体扫描单独计数，不是空间查询，不能并进查询次数。候选数把重复访问照实累加，不是去重后的目标数，也不是索引内部扫过多少格。攻击体和剑的更新次数是服务端 tick 入口次数，含休眠和等待激活的实例，不是当时活着的实体总数。

没有打开采样 tick 时，命令和网络任务不计入。延迟结算只落在它真正执行的那一格；那一格不在窗口里就不记，也不会按施放时间补回去。会话里已经打开、却没有等到 END 的 tick 会整格丢掉细项，只增加未完整 tick，避免出现没有 tick 分母的明细。

## 对比两次结果

调试日志会改变耗时。对比时保持 `/shulog` 和其他设置一致。这个记录器不读取、不打开、不关闭 DebugLog，也不使用它的客户端状态来代表服务端。

## 调用边界

关闭时，`isRecording`、`begin`、`end`、`add` 不读 nanoTime，也不分配。非服务端采样线程一律无操作。计时包住原逻辑，包括早退和异常；异常继续向外抛。不要为了关闭采样而跳过玩法。需要列表长度这类数值时，先看 `isRecording`，再 `add`。`add` 的零和负数不起作用，调用方不要为了计数把业务表达式再执行一次。

## 首版不包括

- 原版实体追踪，真实网络发送完成、字节数和延迟，以及客户端解码、渲染、FPS。
- `EXPLICIT_SEND` 只是事件、声音、粒子这些业务调用的墙钟，不能换成包数。`entityData.set` 和 `setPos` 不算网络发送。
- `ModNetwork.sendToPlayer`、`FireVisualRelay`，以及模组里其他发包位置。显式同步只覆盖 `TechniqueHitSettle` 的事件、声音和粒子调用。
- 真剑抛出时的生成，以及 `HitVolumes` 的视觉体生成。攻击体生成只计 `TechniqueHitSpec`，幻剑生成只计 `PhantomSwordEffect`。
- 活跃实体实时总量、休眠与活跃分开统计、每个术式或每个玩家的明细、内存分配和 GC 的独立耗时、空间索引内部候选访问量，以及没有列入的查询和碰撞。
- 更新次数不是活跃实体总数。
- 待命之前、停止之后，以及服务器退出时那一格残缺 tick。退出时没录完的 tick 会随本次会话丢掉，不会自动写成文件。
- 这不是全模组 profiler，也不是原版追踪器 profiler。

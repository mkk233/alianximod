## 结论

需要一项限定返修：领域接触伤害在已经造成伤害后抛出异常时，当前 finally 无条件退回未提交收据，可能形成已发生伤害但不收费。该行为不满足本次已批准的成功伤害支付边界。先修这一项并收束写入，再安排后续校验与最终统一编译；本轮不把当前版本认定为完成。

集中 Cursor 审查未列 P1/P2，但作者和审查者均明确确认了这条异常路径。本裁决将其列为 P2：它不是推测某个未知接口可能出错，而是已确认异常进入该路径时，当前账务结果与已发生伤害不一致。没有必然抛出的现有证据，会限制复现概率判断，不会使该路径成为正确行为。

## 唯一必须返修项

位置：src/main/java/com/bslx/XueXiMod/shu/technique/release/domain/DomainContactBilling.java 的 apply，报告定位为第 99–107 行。

当前正价路径已由同轮事实补齐确认：charge 预留 → confirmDamage → 返回 true 才 retainShare 并设置 committed → finally 对所有未提交情况退款。review-final.md 第二节“预留发生在返回真之后”是笔误，以 review-order-fact-final.md 的明确顺序为准，不能据笔误增加第二个问题。

问题在于确认方法异常退出时，confirmed/committed 赋值没有完成，即使伤害已经生效，finally 仍退款。反过来，简单改成“只要抛异常就扣钱”也不合格，因为异常可能发生在任何伤害实际生效之前。

返修应维持原有支付语义：

- 正常返回且确认正伤：提交一次；致死照常收费。
- 明确未生效、被取消、无敌帧拒绝、最终零伤：退款一次，不发附魔载荷。
- 伤害调用异常退出：结算层必须仍能保留本次已发生伤害的确认结果，并据此提交或退款，不能把“异常”直接等同于“零伤失败”。
- 异常处理不能直接补血来伪造回滚，也不能吞掉异常或发出成功载荷来掩盖失败。
- 仍使用独立收据并退回原资金来源，不改变 MagicPool 或全局退款规则。

限定改动面：首先是 DomainContactBilling.java；若现有 hurtConfirmed 只能正常返回布尔值、不能在异常退出时提供可靠的已发生伤害结果，则允许由同一作者对 TechniqueHits.java 的确认伤害辅助接口作最小补充，并让领域计费使用该补充入口，保持其他调用者行为不变。若该结果只能由 TideMarkDamageScope 等更底层作用域保留，作者应先报告精确必要文件及原因，由主会话明确扩展文件所有权后再改；不得借此重构所有伤害或计费路径。

需特别注意：仅见到了正值伤害事件，不自动证明后续已经完成扣血；仅比较前后生命值也不自动覆盖吸收值和同步回调造成的变化。返修者应依据现有伤害确认机制给出准确的提交证据，不能用另一种猜测替代当前无条件退款。这里要求履行既有支付契约，不新增玩法规则。

返修最终反馈应分别说明“伤害生效前异常”和“伤害生效后异常”的资金结果，说明确认依据及异常如何继续传播；具备可控验证入口时，针对这两个分支做最小定向验证。没有执行的验证如实记为未执行。

## 结论

同一项 P2 尚未完全关闭，必须再作限定返修：伤害调用已经实际扣减吸收值，但在 setHealth 返回前异常退出时，当前跟踪标记仍为 false，随后退还已预留费用。扣除吸收也是该次伤害已经生效的一部分，不能将这一明确的异常路径当成未发生伤害。

这不是新增计费设计，也不是要求修改正常返回的最终零伤规则。返修仅补全第一轮已要求的“异常退出时，根据实际已发生伤害决定提交或退款”。修完并收束写入后，再安排剩余额度内的集中复核及最终统一编译；当前不能作该 P2 已解决的交付结论。

## 已解决部分

根据最终报告，两个 actuallyHurt 的 setHealth 返回后已有提交信号，较晚的 VanillaGameEvent 路径已移除。因此 setHealth 返回之后、统计或后续处理抛出时，不再误退费用。伤害调用的动态分派和次数、无跟踪调用兼容、异常继续抛出及异常不发成功载荷，均已有 Cursor 定向证据，本轮没有据此提出新问题。

## 仍须补齐的具体窗口

Cursor 对本地 Forge 1.20.1-47.3.33 的核对表明：LivingEntity 与 Player 的 actuallyHurt 都先在偏移 56 执行一次 setAbsorptionAmount，之后才进入 onLivingDamage 和更晚的 setHealth。吸收确实减少且该次写入返回后，后续回调、饥饿、战斗记录等仍可能异常退出，生命值提交钩子尚未触发，现有 healthApplied 为 false，导致退款。

修复必须识别这一次实际吸收减少，不能把“执行了吸收 setter”或“参数是非负数”当成伤害证据。没有减少、只是等值写入或增加时，不能设置已发生伤害标记。

## 具体接受条件

1. 只在本次受跟踪的伤害帧内，确认目标的该次吸收写入确实完成且值真实减少，才记录吸收已生效。继续保持现有目标、来源和调用帧匹配；嵌套伤害不能污染另一笔收据。
2. 异常退出时，只要本次生命伤害提交或吸收实际扣减已有可靠证据，就提交原预留费用一次；两者同时发生也只提交一次。完全没有已生效证据则退款一次。
3. 吸收为零、等值 setter、吸收增加或在实际写入前异常，不能仅因走到钩子而收费。核对以相关实际写入为单位，不能只在整个 hurt 调用两端取差，把嵌套回调或其他变动错算成本次伤害。
4. 正常返回仍采用既有 hurtConfirmed 布尔结果：确认正伤提交；最终零伤、取消或无敌帧退款。正常返回时吸收被扣但最终事件数量为零，仍按原布尔语义处理，本次不借异常返修改动它。
5. RuntimeException 与 Error 按原异常继续传播；异常路径不发火种或附魔成功载荷，不补血、不回填吸收，不吞异常。收据保留原来源退款能力，预留、提交或退款均不重复。
6. 原 actuallyHurt 的动态分派及调用次数不变；没有领域监视时，不改变其他伤害调用的结果或无敌帧语义。既有 setHealth 返回后信号必须保留，不能修吸收时重新打开已关闭窗口。

返修最终报告需说明两类实体的具体采集位置，并给出以下分支的依据或定向验证结果：实际吸收减少后异常、吸收未减少后异常、setHealth 返回后异常、正常最终零伤。实际未执行的测试明确写未执行，不能用静态推导充作运行通过。

## 文件放在哪里

平衡是独立 JSON，不写入现有 toml。

| 用途 | 位置 |
| --- | --- |
| 整合包模板 | 游戏目录下的 `defaultconfigs/xueximod-balance.json` |
| 这个世界真正生效的文件 | 世界根目录下的 `serverconfig/xueximod-balance.json` |

`xueximod-common.toml` 和 `xueximod-batch-terrain.toml` 保持原义。潮湿飞行豁免、示例用的泥土记录、魔法数字和物品列表都不是这套伤害或魔力配置。地形破坏开关也仍只服务原来的地形机制。

优先级：

1. 世界文件已经存在：只读它。模板后来怎么改，都不覆盖这个世界里已经写下的值，也不删除认不出的键。
2. 世界文件还不存在：把模板复制过来。新世界走这条。
3. 模板也不存在：按已经封存的声明生成一份完整默认模板，再复制成世界文件。

没写进世界文件的术式或字段，在内存里用代码默认值。

## 最小 JSON

`schemaVersion` 当前只接受 `1`。顶层是 `schemaVersion`、`global`、`techniques`。术式用完整稳定 ID，内部是扁平参数名。不要用中文名或制作表编号。

下面这份可以单独作为世界文件。它只把刺击 `sword_thrust` 的伤害倍率写成 `1`（也就是代码默认）。没写出的术式和字段都回代码默认，所以它不会改掉其他术式。完整目录以游戏生成的模板为准，不必手抄 62 个术式的原始数字。

```json
{
  "schemaVersion": 1,
  "global": {
    "damageMultiplier": 1,
    "manaMultiplier": 1,
    "cooldownMultiplier": 1
  },
  "techniques": {
    "sword_thrust": {
      "damageMultiplier": 1
    }
  }
}
```

`sword_thrust` 的 `damageMultiplier` 和 `lifetimeTicks` 都是已经声明的键。`lifetimeTicks` 的代码默认是 4，来自刺击登记寿命。要改寿命就在同一对象里加 `"lifetimeTicks": 4`，再改成想要的正整数。

已知别名 `water_open_ring` 会并进 `water_blade`。两份同时存在时，正式 ID 的整份对象优先，别名被忽略并警告。只有别名时，按 `water_blade` 收录并警告。

## 何时生效，坏文件怎么办

改完存盘后，下一次服务器启动或重新打开单机世界才生效。世界开着的时候改磁盘，这一局不变。本版不在世界进行中热替换快照，避免收据、燃烧账、剑和命中实体混用两套数。

服务端在内置术式和外部内容都登记完、目录封存之后装入这份快照。玩家登录时，服务端把已经接受的覆盖值同步给客户端（网络包号 15，通道协议仍是 `"2"`）。客户端用同一份已封存声明再解析，只安装客户端快照。断线只清空客户端。单机集成服务器不会因此清掉服务端快照。客户端不能把修改送回服务端。

因此，装配界面、术管理、技能书和 `/shu list` 应显示这一局已生效的基础伤害和基础冷却。这个同步还没有在游戏里核对。

整份 JSON 不是对象、缺少 `schemaVersion`、版本不是 `1`，或 `techniques` 不是对象：保留原文件，日志记错误，这一次安装代码默认快照。不会把损坏文件重写掉。

单个字段非法：警告，只让该字段回到自己的默认。其余字段仍用文件里的值。未知根字段、未知术式、未知参数同样警告并忽略，原文件保留。非有限数、越界、整数键上的小数，都算该字段非法。

冷却还有一条：代码默认不是 0 时，配置里的 0 非法并回退。代码默认本来就是 0 时，0 可以留下。正冷却经过不是 1 的全局倍率后，舍入结果小于 1 就提到 1。全局冷却倍率恰好是 0 时，正冷却的结果是 0。

## 三个全局倍率

全局只有这三项，代码默认都是 `1`，范围都是 `0` 到 `1000`。术式对象里不能再声明 `manaMultiplier` 或 `cooldownMultiplier`。

| 字段 | 用在哪里 | 次数 |
| --- | --- | --- |
| `damageMultiplier` | `damageContribution`，以及无潮印武器印记那一份额的 `globalDamageContribution` | 各一次 |
| `manaMultiplier` | `manaCost` 形成单价时 | 一次 |
| `cooldownMultiplier` | `cooldownTicks` 读取基础冷却时 | 一次 |

倍率恰好是 `1` 时，伤害保持原来的 `float` 收窄，费用和冷却保持原整数。任一伤害倍率不是 `1` 时，乘积按半远离零收到小数点后 4 位再转成 `float`；结果非有限或大于 `1000000000` 会拒绝。费用和冷却在倍率不是 `1` 时按半远离零收成整数。费用 `0` 仍是 `0`。溢出不回绕。

没有全局的实体数量、复制份数、几何能量或尺寸倍率。

## 每个术式都有的标准键

标准键由公共目录在封存前补上，默认来自术式原来的 getter，不是另一份手抄数字。

| 键 | 种类 | 单位 | 代码默认 | 范围 | 谁读取 |
| --- | --- | --- | --- | --- | --- |
| `cooldownTicks` | 整数 | 刻 | `getBaseCooldown()` | `0` 到 `1200000`；只有原始默认是 0 才接受配置 0 | 基础冷却。其后才是附魔反应和法杖缩减 |
| `manaCost` | 整数 | 魔力 | `manaCost()` | `0` 到 `1000000` | 报价大于 0 的单价；领域开域、水牢成功、自身状态 |
| `damageMultiplier` | 数字 | 倍率 | 字面量 `1` | `0` 到 `1000` | 只在该术式确有伤害贡献时声明 |

`damageMultiplier` 写成 `0` 时，这一笔贡献可以是 0。它仍是攻击贡献，不会把术式改成规则，也不会拆掉领域绑定。

调整 `damageMultiplier` 不改变 `manaCost` 的默认。默认魔力仍按原来的优先级，用尚未缩放的基础伤害推导。两件事要分别写。

`Technique.baseDamage()`、`manaCost()`、`getBaseCooldown()` 仍返回原始结构值。宿主识别、附魔边界和默认耗魔继续读这些原始值。

水幕和水环的 `manaCost()` 仍是显式 0，所以标准键 `manaCost` 的默认也是 0，宿主预扣仍是 0。它们真正的费用是下面的 `spawnManaCost` 和 `upkeepManaCost`。改 `manaCost` 不会改水幕、水环的生成费和维护费。

有 `damageMultiplier` 的稳定 ID：

`sword_thrust`、`sword_horizontal_slash`、`sword_vertical_slash`、`movement_dash`、`magic_arcane_missile`、`test_sustained`、`heat_beam`、`space_cut`、`parasite_seed`、`tide_sever`、`stone_hammer`、`metal_needle`、`fire_orb`、`fire_burst`、`water_yielding_ribbon`、`water_weeping_arc`、`water_blade`、`fire_meteorite`、`fire_shock_ring`、`fire_spark`、`phantom_sword`、`water_prison`、`fire_liaoyuan`、`fire_fentian`、`fire_liaoli`、`fire_scorch_field`、`fire_kindle`、`fire_detonate`、`fire_cool`、`tide_mark`、`vine_mark`、`sinking_edge`、`keen_mark`、`magic_ignite`。

## 首版不开放

不能写成「所有数值可配置」，也不能写成「所有攻击都走同一种伤害」。

不开放：结构角色、结算顺序、命中去重、账本规则、复制份数、双重份数、一分为三份数、原生元素反应表、装配消耗、解锁等级、炉心热量公式和内部属性改写、几何能量、只用于画面的常量、地形开关、寄生种子份数（仍是 3）、引燃每段燃料需求、焚天段数上限和档位上限、种火容量上限本身、已废弃的领域维护费、潮印条数、引爆系数、幻剑飞过 64 格才弃置、插地深度、水幕前放距离、陨岩重力和俯仰、喷涌重力和半角。

没有被飞行读取的弹速不能当成飞行速度。登记了却没有消费者的厚度，例如飞弹厚度 0.1、火球厚度 0.4，没有做成键。

## 伤害、费用各自只乘一次

每一笔先按原公式得到原始金额，再换成已配置金额：

已配置 = 原始贡献 × 该术式 `damageMultiplier` × 全局 `damageMultiplier`

之后只合并，不再乘平衡倍率。命中出口和原版受击监听不对整刀再乘。账本最后仍是「这一份已配置伤害 × 命中份数」，份数不是另一次平衡倍率。

普通链拆成三笔，各乘一次后相加：

- 宿主：同属性处理之后的宿主攻击，加上武器加成，用宿主术式。
- 共享附加：火、木、土、金在普通链上共用一笔，不是每条各加一份。归属是**第一次把这笔钱从无到有建立出来的那个术式**。后面的同属性附魔仍按原规则修饰这一笔，但它们的伤害倍率不再乘它，宿主倍率也不包裹它。来源在建立时记下，不看配置之后是不是 0。没有这笔贡献时来源为空，金额为 0。
- 潮印：用 `tide_mark` 缩放原来的「条数 × 2」这一笔金额。条数本身不变，潮湿和水势仍看条数。

没有附魔时，法杖调整后的整段宿主金额缩放一次。

接触附魔是另一条公式：每一格原来的加数按该格术式各缩放一次。不要写成「每条附魔在所有场合都独立加伤」，也不要把普通链改成按格相加。

领域光环按光环来源缩放一次，再加到已经配置过的基础金额上。哪些命中可以吃到领域加伤，范围不变。A2 报告这一点做在 `DomainAuraResolver`。B 的清单写明该文件不归 B。本文不对这两份报告再做正确性判断。

火伤按每条真实贡献转换，不在总出口补乘。燎原本休先按当时炉心合成再缩放；火种段、焚天段、引燃段在挂载时缩放整段。引爆、燎里火种、灼地接触和主动冷却蒸汽各自缩放自己那一笔。燎里的物理刺击和火种伤都归 `fire_liaoli`，各一次。炉心公式本身不开放。水牢压强在产生那笔环境伤害时按 `water_prison` 转换一次，仍没有攻击者，不绕过无敌帧。

公式系数（引燃段伤基数等）先替换默认值，代入原公式，公式输出才是原始贡献。这不是两次伤害倍率。

魔力在单价形成时乘一次全局魔力。之后的份数、成功目标数和维护次数沿用原账单。退款退这一次收据上的金额，不按新配置重算。魔力池本身没有倍率。

冷却先取 `cooldownTicks`（含一次全局冷却），再做原来的反应倍率和法杖缩减。法杖缩减里不再乘全局冷却。

## 原版攻击、原版燃烧、旧存档

有潮印的武器印记，只在原版主目标那一刀上**加上**已经配置好的潮印金额和共享附加金额。不乘原版那一刀，不加到横扫上，也不因此打出第二刀。

没有潮印时，原来的额外一刀仍在。其中的武器份额没有宿主术式，只乘一次全局伤害倍率。共享附加用的是保存时已经配置好的金额。原版最初那一刀不套全局伤害倍率。

玩家被点燃之后，原版自己产生的燃烧伤害不归这套全局伤害倍率管。`magic_ignite` 的 `burnSeconds` 只改着火时长。

幻剑生成时，先乘场上的帧倍率，再按 `phantom_sword` 把武器伤害转换一次并保存。飞行、召回和读档不再乘。旧存档里的剑伤害按已写下的最终数值使用。

武器新印记写入 `Version = 1`，以及已配置的 `Attack`、`Added`、`TideDamage`。`Tide` 仍是条数。没有 `Version` 的旧印记，主刀附加按旧的 `Tide * 2 + Added` 使用，不再乘。有版本但缺少 `TideDamage` 时，潮印金额回退为 `Tide * 2`。

燃烧新挂载写版本 3，金额已经配置过。缺版本、版本 1 和版本 2 按旧最终金额读取，不再乘。其他版本整份丢弃。

保存时乘过的，读取时不能再乘。

## 给新术式

公共封存发生在 `XueXiMod.commonSetup`：先 `ModTechniques.registerAll()`，记下内置术式，投递 `RegisterXueXiContentEvent`，再调用 `BalanceCatalog.sealAfterContent()`。

`sealAfterContent` 的顺序是：为每个已登记术式补标准键，调用 `ModTechniques.declareSpecialBalances()`，再调用 `EnchantmentDefinitions.declareBalance(BalanceRegistry.current())`，最后 `BalanceRegistry.seal`。新术式不要自己调用 `seal`，也不要在静态初始化里读取有效配置。

标准冷却、标准费用和适用的 `damageMultiplier` 不要在专项里再声明一次。零伤规则、剑来、万剑归宗不要打开伤害倍率。只存在生成费或维护费、而 `manaCost()` 不是收费依据时，不要用标准 `manaCost` 冒充那笔费用。

本仓库里的专项从自己的登记方法进入 `ModTechniques.declareSpecialBalances()` 或 `EnchantmentDefinitions.declareBalance(BalanceRegistry)`。火场半径、灼地寿命和半幅、幽冥产种与周期、种火数量、引燃段参数、蒸汽半径、缠枝控制时长、点火秒数已经由附魔侧声明，不要再声明同名键。

外部内容在事件里登记专项。标准键仍由后面的封存补齐。旧的 `registerCast` / `registerEnchantment` 可以单独使用；没写专项时会得到标准冷却、魔力，以及基础伤害大于 0 时的伤害倍率，并收到专项未声明的警告。不要为了旧入口伪造范围或速度键。

下面的签名与当前公开方法一致。`heat_beam` 用它已经存在的长度和命中间隔，作为最小例子。新 ID 换成你的稳定 ID，默认值换成该效果里的原常量。

```java
BalanceRegistry.declareSpecial(TechniqueBalanceSpec.builder("heat_beam")
        .numberParameter(BalanceKeys.BEAM_LENGTH, RawDefault.literal(6.0d),
                BalanceBound.positiveSize(), BalanceUnit.BLOCKS, "热光束长度")
        .integerParameter(BalanceKeys.HIT_INTERVAL_TICKS, RawDefault.literal(10),
                BalanceBound.positiveTicks(), BalanceUnit.TICKS, "热光束命中间隔")
        .build());
```

外部事件用的是同一份规格，入口不同：

```java
event.registerBalance(TechniqueBalanceSpec.builder("your_stable_id")
        .numberParameter(BalanceKeys.BEAM_LENGTH, RawDefault.literal(6.0d),
                BalanceBound.positiveSize(), BalanceUnit.BLOCKS, "长度")
        .build());
```

`registerBalance` 声明失败时返回 `false` 并记日志，不另建一套目录。

读取时，专项尺寸用 `number` / `intValue`。伤害传入的必须是还没乘过本配置的原始金额，返回值不要再送回去：

```java
double beamLength = BalanceService.number("heat_beam", BalanceKeys.BEAM_LENGTH);
int hitInterval = BalanceService.intValue("heat_beam", BalanceKeys.HIT_INTERVAL_TICKS);
ConfiguredDamage configured = BalanceService.damageContribution("heat_beam", RawDamage.of(rawAmount));
float dealt = configured.amount();
int unitPrice = BalanceService.manaCost("heat_beam", BalanceKeys.MANA_COST, rawUnitPrice);
int baseCooldown = BalanceService.cooldownTicks("heat_beam", rawCooldown);
```

链上已经配置过的金额用 `ConfiguredDamage` 继续传递。`plus` 相加，`timesHitCount` 乘命中份数，`retained` 表示旧存档或已经保存的金额。这三步都不再读倍率。

没有宿主术式、但又是本模组打出的额外武器份额，用 `BalanceService.globalDamageContribution(rawAmount)`，只乘全局伤害一次。不要对原版普通攻击那一刀调用它。

魔力键和 `cooldownTicks` 不要用 `number` / `intValue` 去读，那会绕过全局倍率并抛出。`number(id, "damageMultiplier")` 只返回术式自己的倍率，不含全局倍率，不能再乘到 `damageContribution` 的结果上。

两侧都安装了快照、而当前线程没有绑定时，必须使用带 `BalanceSide` 的重载。集成服务器的服务端刻和客户端刻各自绑定，不能共用一个「当前侧」。

## 边界

| 工厂 | 区间 |
| --- | --- |
| 倍率 | `0` 到 `1000` |
| 魔力 | `0` 到 `1000000` |
| 冷却刻 | `0` 到 `1200000`，只有原始默认是 0 才接受配置 0 |
| 正刻数 | `1` 到 `1200000` |
| 尺寸 | 允许 0 时是 `0` 到 `512`；必须为正时是大于 `0` 到 `512` |
| 速度，块/刻 | 允许 0 时是 `0` 到 `64`；必须为正时是大于 `0` 到 `64` |
| 卸伤比例 | `0` 到现有封顶 `0.6` |
| 单位比例 | `0` 到 `1` |
| 公式用的平直伤害 | `0` 到 `1000000` |
| 个数 | 声明时给出的闭区间；火种数量上端是现有上限 100 |

非有限数拒绝。

## 待用户实测

下面每一步都还没有人在游戏里做过。通过与否以实测为准。默认不打包、不代为启动游戏。

1. 不改文件，或三个全局倍率和术式字段都保持默认。同一套操作下，伤害、耗魔、冷却应与接入这套配置之前一致。
2. 只把 `sword_thrust` 的 `damageMultiplier` 改成 `2`，其他键不动。重新打开世界后，刺击伤害应提高，刺击的默认耗魔不应跟着变。再把该术式的 `manaCost` 单独改掉，耗魔才应变化。
3. 把全局 `damageMultiplier` 改成不是 `1` 的值并重启。已配置的术式伤害应只乘这一次。空手、没有本模组印记的原版普通攻击不应被这套倍率改掉。点燃之后原版自己跳的燃烧伤害也不应被改掉。
4. 一分为三或多重命中只应按命中份数累加已经配置的伤害，不应每份再乘一次全局倍率。火、木、土、金同时附在普通链上时，共享的那一笔附加只吃第一个建立它的附魔的伤害倍率。接触附魔仍按每一格分别变化。幻剑生成后再改倍率并召回，已经存在的剑伤不应再乘一次。
5. 服务端改好并重启后，客户端登录看到的装配说明、术管理和 `/shu list` 应与服务端这一局一致。客户端断线不应把单机世界里的服务端数值清掉。

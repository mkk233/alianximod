本文是代码线、美术线和批量模式的唯一流程正文。`AGENTS.md` 与 `.grok/skills/max-dispatch/SKILL.md` 只保留硬约束、入口和速查，不另定状态；三者冲突时以本文为准。游戏 MCP 限制和术式技术约束以 `AGENTS.md` 第 4–6 节为准。

## 讨论与执行

- **直接讨论设计**：用户探讨玩法、机制、需求、方案或取舍时，主会话直接理解、推理、回答并提出建议；不派子代理，不以先走执行流水线为前提，不领表、不改代码、不编译、不迁表。仅因提到某个术式、制作表或设计较复杂，不自动转执行。这类交流不是正式复审。
- **执行任务**：用户明确要求按表制作、落地实现、修复、编译或其他执行工作时，走后文流程。已明确授权的执行不重复要求确认。
- **混合消息**：主会话先直接回答设计部分，已授权且设计明确的执行部分再派发。
- **后续消息**：先判断是否仍在原授权范围内。范围内 follow-up 和返修沿用原 batchId/taskId，按第 11 节续用原代理或交接；超出范围按现有授权判断，不自动扩大，也不逐项机械追问。
- **防绕额度**：对现有批次做正式正确性或验收复审、或返修后的正式复审，即使以讨论形式进行，仍按第 1.1 节计数。

## 1. 角色与工具

- **用户**：填写「待制作」；集中回复视觉和实质设计选择；确认美术版本；做游戏实测并判定完整术式是否完成。
- **主会话**（执行任务）：调度；开批指定唯一记录者（维护批次记录、文件所有权和复审记录）与唯一制作表写回者；读记录、单个符号或单份文档；汇总已跑命令、未跑项和环境阻塞；在额度内做集中逻辑复核。不通读整仓，不改 Java，不跑 Gradle，不亲自写表；执行受阻时也不接管。
- **唯一裁决者**（`gpt-6-astra` · `high`，只用于执行任务）：仅在对应阶段额度未用完时裁决难点和新需求，同时只开一个。根因不明、改动牵涉多处、接口或架构未定、并发或 NBT、需求含糊、改错成本高时先交给它，再交 Grok 落地。不可用时按第 11.1 节降级链；额度用完后，无法在已批准设计内推进的事项只报告阻塞。用户偏好选择集中问用户，不逐项追问是否开工。直接讨论设计不交给它。
- **Flash 读取**：专门读文件、成片代码阅读、定位和事实摘要，可按独立范围并行；无写文件、编译或写表权限，不作正式正确性裁决。嵌套与事实包见第 11.4 节。
- **Grok 执行**（本文「Cursor」均指此原生执行子代理角色）：代码实现、修复、实现中的定向检查、额度内的执行复核、编译和制作表写回。不用 computer-use 操作 Cursor 客户端。
- **代码正式复审**：Opus，在实现阶段额度内执行；降级只到 Astra high，不交 Google 模型。非代码方案的第二意见见第 11.1 节。
- **美术**（Gemini Carbon 首选，降级链见第 11.1 节）：绘制、建模、二维/三维预览和视觉效果调整，不交 Grok。实际制作先读 `C:/Users/baishang/.codex/skills/xueximod-art-preview/SKILL.md`。二维用 Aseprite，用户指定时用 Photoshop；有空间关系的素材（贴图或粒子也算）都要真实 Blockbench 示意。不用 ImageGen 代替绘画或建模。
- **游戏**：效果由用户测。默认不 `build`、不打 jar、不 reobf、不发布、不 `runClient`、不启动游戏。离线任务不要求游戏桥在线；用户明确要求游戏内操作时按 `AGENTS.md` 第 4 节。

模型 ID、档位、协议入口和回执只以第 11 节为准。喜鹊只承接底层账户、路由和回退，不代管业务权限、依赖、文件所有权或复审额度。

### 1.1 正式复审额度

- **上限**：设计最多 2 轮、实现最多 3 轮，分别计数，不必用满。没有独立测试阶段，没有测试或视觉审核额度。
- **计什么**：一次正式的正确性或验收条件审查并给出结论算一轮，无论通过与否；该轮中的读取和汇总仍算同一轮。返修后的每次正式复审各算一轮。开工前方案裁决计设计，代码复核计实现，不因执行者是 Astra 一律算设计。父子代理各自独立重审不能并成一轮。调用裁决前先看实际阶段额度。
- **不计什么**：领取、读输入、Flash 事实采集、状态对账、协调、阻塞通报、转达结果、美术制作、用户选稿和游戏实测。不得借这些名义再审正确性。
- **共享且不重置**：主会话与全部子代理共享本批 batchId 的计数。按文件、术式、ready 子批、新会话、新代理、新 taskId/attemptId、拆项、改名、重启、换模型或另开 batchId 都不重置；版本变化和返修承接原计数。已获得的用户授权在其范围内继续沿用。
- **时点**：额度未用完或已获追加授权时，等本阶段已派发且可推进的任务全部返回最终反馈（或已交接）、相关写入收束后集中复审；只等当前阶段，不等尚未开始的阶段。阻塞项单列原因和下一步，可推进项组成 ready 子批；拆子批不重置轮次。需止损的阻塞或风险可立即通报，不算另开复审。
- **用完之后**：当次不再自动追加该阶段复审，不交 Astra、Grok、其他子代理或新会话继续审，也不把重审改称咨询、定向检查、设计讨论或跨阶段改名。已授权的返修、实现、编译、必要定向检查、美术制作、用户确认和确认版接入照常完成；记录「本阶段额度已用完，返修结果未追加复审」，保留未决问题与缺少的验证。额度耗尽不是完成，不掩盖编译失败或实现未完成，不豁免第 8 节任何条件，也不能写成复审通过；旧版本的通过结论不套用到返修新版本。条件齐全时，没有额外复审或独立测试不单独阻挡迁待验收。
- **追加**：确有必要时向用户简明提出已用次数、未决问题、追加原因、拟复审范围、执行者和轮数；默认直接交付现有结果，不机械追问。沉默、继续返修或报告完成都不是授权。授权后只在批准范围和次数内复审，累计记录、不重置原计数；执行者按第 11.1 节：代码交代码正式复审角色，非代码交第二意见角色；用户另选时按授权执行。
- **记录**：只由唯一记录者追加，每条正式判断写日期、阶段、轮次、输入版本、问题与结论；子任务不改额度。交付分开写执行者报告的结果与已做复审的结论。`docs/开发记录/协作流程优化-20261103/记录.md` 只记那次流程改进自己的额度（设计初审 1/2；实现正式复核 1/3 已发现问题，返修承接），不影响其他批次。
- **例**：设计初审 1/2，返修后复审 2/2，之后不能自动开第三次。实现初审 1/3，返修后 2/3，再返修后 3/3，之后不能自动开第四次。

### 1.2 派发后的等待

派发后只等最终反馈：不读实时思考、流式输出、工具调用详情或中间代码，不重复扫 diff，不边做边审。必要时只做低频最小状态检查（运行中、已完成、失败、需要输入），状态无变化不展示心跳。只有实际失败、阻塞、需要用户输入或用户明确要求时，才按需读取必要信息或原始日志并记录其位置。本文的「跟踪」「等待最终反馈」「进度采集」只指这些，不计复审。单次等待超时不是任务结束；接收与续行责任见第 11.5 节。

## 3. 领取、编号与状态

唯一键是 `B` 编号。工作表名和行号只记录领取时的位置。技术列非空不表示完成，也不构成新任务。四张状态页内每个 `B` 只出现一次。档案页出现相同 `B` 是合法的，不纳入四页重复判定；档案内部每个 `B` 只有一个首次快照。「资源状态明细」仍按既有规则关联同一编号的后续明细，不把明细重复当成状态页重复。任务数量、领取防重和行数守恒只计这四张状态页。

领取前读完四张状态页：

1. 有效行：第 3 行及以后，`B` 去首尾空白后非空，且四页中该编号只出现一次。
2. 问题行：`B` 空但同行有其他内容、编号在四张状态页内重复、四页之间跨页重复。记入本批「待澄清」，其余有效行继续。不自动重编号，不改历史编号。档案页的相同 `B` 不算这个问题。
3. 新任务只从「待制作」的有效行领取。不从已完成补队列，不把历史已完成当成这次已经游戏通过。
4. 用户说按表批量制作时再领取。默认每项是完整术式，包含确认版归档和授权范围内接入。用户写明仅素材时，该项按纯素材范围做。已有设计和已批准版本直接使用。

状态只按页移动：

- 领取时按 `B` 核对四张状态页，以及已有批次记录和交接记录。新编号首次领取前，先按第 8 节把当时待制作完整原始行和适用的原始资源状态明细留档；捕获失败不能先迁走或丢掉原行。留档完成后、开始该项实现前，按第 8 节把该行从「待制作」实际迁到「制作中」，并重开核对。不能只在进度文档里标已领取。写回受阻则该项不作为新项反复派发，记下原因，其他独立项继续。设计、二维、三维尚未确认也留在制作中，细节写批次记录。
- 只有第 8 节的迁移条件全部满足，才从「制作中」迁入「待验收」：功能实现、独立美术制作、同版本用户视觉确认、确认版归档和运行接入均已完成，相关写入收束，必要实现检查、最终编译和第 2 节需求快照齐全。临时美术只算占位；缺美术、缺确认、确认版未接入、编译失败、实现未完成或快照缺失均留在制作中。没有额外复审、没有独立测试，只有在上述条件已满足时才不阻挡迁移。额度用完只整理 Cursor 结果并注明未追加复审，不能写成已经新增复审通过。进入前按第 2 节保存详细需求快照，再转换表内 `N`/`O`。
- 用户游戏实测通过后，才迁入「已完成」。
- 返修回到「制作中」，只重做并重验受影响部分。表内 `N`/`O` 按第 9 节从最近一次已批准的详细需求快照恢复。缺快照则待澄清，本轮不迁移该行。不动历史已完成。
- 纯素材项没有代码、编译和游戏阶段。最终素材验收通过后进入「已完成」。

批量是连续推进互不阻塞的项。等视觉确认的项停在制作中；其他项继续。静默不是批准。可以集中交出一批预览，仍要等用户回复后才归档为确认版。二维确认不等于三维通过。

## 4. 最小输入与底座

领取时至少抄下：编号、名称、来源页、行号、当时表哈希与文件最近更新时间、`N` 功能描述、`O` 特效意图、`DV` 备注原文、最新已批准需求版本、类型、属性、释放种类、释放标签、弹道、链上角色，以及本项实际依赖的尺寸、持续、能量缩放和其他依赖列。缺哪一列，按这项是否用得到判别。完整术式缺功能描述或链上角色，该项待澄清，不补猜。纯图标可以没有链上角色。不要求 144 列全填。同一编号在「资源状态明细」里还有记录时，按编号一起读取。行在待制作或制作中时，抄下的 `N`、`O`、`DV` 保持用户原文。

带下拉约束的枚举列，中文取值只许用「数据表」名称列。`N`、`O`、`DV` 是自由文本。代码对应执行时的现行源码；不一致则该项停在制作中，交给该阶段额度内的唯一裁决者（第 11.1 节）。额度用完则报告阻塞，不再请脑子重审，也不自动交给 Cursor 复审。表内参数是任务输入，不是覆盖底座的授权。旧设计文档和旧表同样不能单独授权改底座。制作表里的数值也不是配置键清单；新术式的重要平衡值按下面的配置约束声明，不从缺列补猜键名。

新术式在 `ReleaseDefinitions` 登记 `ChainRole`，走同一套收集和结算。结算顺序是索敌、弹道、规则、攻击。枚举声明顺序不是结算顺序。「弹道可被修改」为否时，斩击只改生成位置。落点、交错、一分为三和附魔不按术式 id 分叉。共享底座（释放注册、链结算、统一配置读取、公共注册表、语言文件、资源库索引、制作表）先经审查，再由该文件的唯一作者修改。

后续制作的新术式必须兼容配置改动。平衡以每个术式自己的参数为主，全局倍率只少量存在，并且每个全局倍率只应用一次。底座统一读取并应用配置。术式按稳定 ID 只声明自身实际有意义的参数；未配置或缺少配置时使用该参数的默认值。默认配置保持当前行为。伤害参数分成武器或玩家攻击倍率，以及固定伤害。不开放 `ChainRole`、结算顺序、命中去重等结构机制，不把几乎所有内部常量做成可调项，也不提供无效配置键。可调伤害不是结构标志；调整伤害时默认耗魔保持不变。文件位置、schema、已开放字段、生效时机、最小 JSON 和实际 Java 签名都在 `docs/配置平衡指南.md`。本流程不另抄这套说明。编译是否已经通过、游戏是否已经实测，以该指南文首为准，不在这里写成已经成功。

缺列按角色补，仍缺就待澄清：

- 攻击且释放种类是命中体：要有功能描述、特效和链上角色。移动中的命中体为「是」时，补存活 tick 或飞行速度。用到弧带、护体、屏障、领域或附魔时，只抄该分组里这项要改的列。
- 一分为三：功能描述写明汇总的是后面哪一段攻击，不另造伤害公式。
- 双重释放：必须有双重释放再拉段数。
- 落点指定、锁定实体、追踪、垂落改写、三维交错：功能描述写明改的是方向、落点还是下一段。索敌不改生成位置。
- 动作为释放种类：要有功能描述，不要求命中体尺寸。
- 纯素材：要有编号、名称、特效或外观意图、尺寸。链上角色和代码写不适用。

## 5.1 功能占位、正式美术与迁页边界

1. **功能阶段可以占位，不能算整项完成。** Grok 可在已授权实现范围内引用现有可用资源或原版通用效果作临时占位，优先复用，不自行绘制、建模或决定最终观感。记录占位资源/效果、运行引用、用途和待替换项；不覆盖正式资源或已有确认版。即使能施放、逻辑实现或编译通过，也只能报告「功能已实现，美术占位未完成」，条目保持「制作中」。
2. **美术必须单独交付。** 功能实现后，按第 5 节和美术技能派美术角色制作正式二维素材及适用的真实 Blockbench 示意。视觉需求已明确且不存在写入冲突时可与功能开发并行，但两个交付都要完成。用户仅授权功能实现时，报告美术待办并留在制作中，不把局部完成说成完整术式完成。
3. **先展示，再由用户确认具体版本。** 记录素材、源文件、二维预览、适用的 .bbmodel/实际视口预览、交接参数及用户明确回复的对应关系。静默、作者自报完成、模型复审或额度耗尽均不是用户确认。确认后改了观感，须重新展示并确认受影响部分。
4. **确认后接入，才具备迁页资格。** Grok 按确认版交接替换本项占位引用，记录正式归档与游戏运行资源映射；占位不能继续承担本项要求的正式表现。相关写入收束后，由指定编译者对最终版本编译，再按第 8 节写回。预览确认、归档完成、编译通过各自都不能单独证明整项可迁页。
5. **复用不强制重画，但不能冒充完成。** 若现有正式确认版确实覆盖本项现行视觉需求，可在独立美术交付记录中引用该版本、适用范围、预览与已有确认依据；没有覆盖本术式用途的确认依据，或形状、朝向、比例、动画等有变化，仍须按本次实际表现预览并获确认。确实不新增或修改任何视觉表现的纯逻辑项，记明具体理由和现有引用；「没有独立贴图」「只用粒子/代码渲染」不构成豁免，存在新的空间表现仍须真实 Blockbench 示意。
6. **记录拆分进度，不增状态页。** 每个 B 在批次记录分列功能状态、美术状态、用户确认、正式接入状态及下一步。制作中的 N/O 保持完整需求原文，DV 保留用户原话并追加带日期的 `[美术进度] 功能已实现；美术占位未完成；下一步：……`，不得提前改成简句或资源名。占位项不计完整术式完成数，不统计为待验收交付；可单独统计功能完成数。
7. **额度只限制正式复审。** 独立美术制作、用户选稿确认及确认版接入不增设测试或视觉审核额度，也不重置原 batchId 的设计 2 轮/实现 3 轮。已授权的制作可继续；真正的正式正确性判断仍按原阶段计数。额度用完不再复审，但缺少美术交付或用户确认的项仍留制作中；迁页前只核对已有交付记录，不借此重新做正确性审查。

## 7. 并行与统一编译

沿用现有 `org.gradle.jvmargs=-Xmx3G` 和 daemon 关闭。不为本流程修改 Gradle 配置。文档任务不跑 Gradle。编译阶段失败交回作者，不边编边改。主会话把命令全文、退出码、以及这次编译是否晚于最后一次相关写入，写入批次记录。退出码不是 0 时，相关项留在制作中。同时写明未跑项和阻塞原因。没有指定编译者时，记录写「待统一编译」。编译失败则相关项留在制作中，不能迁待验收。编译通过只记录编译结果；还须核对第 8 节的美术、用户确认及正式接入证据，全部具备才迁待验收。占位阶段通过的编译不能代替正式资源接入后的最终编译，不另派独立测试。

## 11. 原生子代理派发与执行回执

自 2026-11-10 起，执行入口是 **Codex 当前聊天的原生子代理工具，启动时直接指定模型**；喜鹊承接底层提供方、账户、路由和已配置回退。调度层不再用 Python HTTP 包装器、Shell 拉起 Cursor/Grok CLI、外部 SDK 进程或旧 `Invoke-CursorTask.ps1` 派发、续跑或等待模型，不新增启动脚本、JSON 协议或后台服务。此限制只针对代理启动渠道，子代理正常使用文件工具、项目业务检查脚本及已授权的 Gradle 不受影响。第 1–10 节的授权、文件所有权、额度、编译、迁表与美术门槛照常生效。

### 11.1 角色与模型

| 角色 | 首选 `model` · `reasoning_effort` | 降级链（首选报错才换） | 职责 |
|---|---|---|---|
| 只读 Flash | `deepseek/deepseek-flash` · `low` | — | 读文件、代码定位、资料抽取、事实摘要 |
| 执行 Grok | `cursor/grok-4.7@500k` · `high` + Fast | — | 实现、修复、定向检查、编译、写表；轻量文本可 `low` |
| 美术 | `antigravity/gemini-4-carbon` | `antigravity/gemini-4-argon` → `gpt-6-astra` · `max` | 绘制、建模、二维/三维预览、视觉效果调整 |
| 裁决 | `gpt-6-astra` · `high` | `antigravity/gemini-4-carbon` → `antigravity/gemini-4-argon` | 额度内困难/架构裁决；故障先由它查根因、给修复方案，再交 Grok 落地；同时只开一个 |
| 代码正式复审 | `antigravity/claude-opus-5-5` | `gpt-6-astra` · `high` | 实现阶段额度内审查代码；**不交 Google 模型** |
| 非代码第二意见 | `antigravity/claude-opus-5-5` | `antigravity/gemini-4-carbon` → `antigravity/gemini-4-argon` | 方案、机制、流程的独立审查 |
| 探索发散 | `antigravity/gemini-4-carbon` | `antigravity/gemini-4-argon` → `gpt-6-astra` · `high` | 用户要求的开放式头脑风暴，不作裁决 |

- 本表与喜鹊路由组「分工」（`smart-split`）同步；改路由组时一并改本表，其他文档不再写死模型名。Gemini Carbon 强于 Argon。
- **子代理不填 `group/...`**：路由组会按意图重新选模型（2026-11-13 实测 `group/smart-split` 子代理被派给了 Terra），只供主会话使用。子代理一律填上表真实模型名。
- **降级**只在首选明确报额度耗尽或不可用时进行，记录原模型、错误与替代模型；额度偏少不提前降级。429、网络或审批失败如实记录，不借降级绕过。Opus 与 Gemini 在 antigravity 分属不同额度池。
- **核实实际模型**看喜鹊日志：`magpie usage --csv --last 30m` 中 `collab_spawn` 行的请求模型与服务模型。不问子代理「你是谁」，在 Codex 里它们都会自称 GPT。
- **Fast** 即 `service_tier="priority"`，与推理档位相互独立；模型 ID 不加 `-fast`，也不把 Fast 改成 `low`。工具没有 tier 参数时沿用本机客户端已配置的 `service_tier="priority"`，不传未知字段；只知道配置值时，不声称后端已独立验证 Fast。
- 每次显式传真实模型 ID，不写显示名「Cursor」「Grok」或旧 CLI 别名；路由组成员写法（如 `codex/gpt-6-astra:max`）不直接当参数，档位放 `reasoning_effort`。
- 表外模型只在用户明确指定时使用；不遍历模型试额度、猜套餐或擅自扩展收费渠道。
- 主会话本身的模型由喜鹊路由组按意图选择，不改变本表的子代理分工和复审额度。美术角色负责产物，不因此算复审。
- 不为每项常规任务单独跑连通性测试，实际任务回执就是执行证据。

### 11.2 协议入口

- **跨提供方模型（Grok、Flash 等）必须走 `multi_agent_v1`**：`spawn_agent(message, model, reasoning_effort, fork_context=false)` 返回代理标识，`wait_agent(targets, timeout_ms)` 等待终态。`fork_context=false` 时，`message` 必须自包含任务包和必要的项目规则。
- **V2（`collaboration.spawn_agent`，参数 `task_name/fork_turns`）不派非 Codex 模型**：2026-11-11 在 V2 下派 DeepSeek Flash 返回 400 `task was sealed`，任务被 Codex 后端封装，代理没有开始工作；同模型同档位 2026-11-10 经 `multi_agent_v1` 正常完成。会话只暴露 V2 却必须使用跨提供方模型时，不在该会话重试、改措辞或提高档位，直接报告阻塞；需由用户调整客户端设置（例如关闭 `multi_agent_v2`）后在新会话验证，调度层不自行改全局配置。Codex 自家模型（Astra）两种入口都可用。
- 先读本次工具的真实 schema，参数名和返回标识不跨版本混抄。保存返回的原值作为代理标识；它不是 Cursor CLI UUID、提供方会话或 HTTP 请求 ID，不编造可恢复的 session。
- **关闭与续派**：收到 final 并登记后即 `close_agent`；Grok 对其下属 Flash 同样处理，交付前列出已关闭的下属标识。返修要用原代理时，`multi_agent_v1` 先 `resume_agent(原标识)` 再续派，用完再关。接口有续派工具（如 V2 的 `followup_task`、其他版本的 `send_input`）时，向原代理续派；不要以为只发消息就必然唤起空闲代理。当前接口只有 spawn/wait 时，范围内返修按第 11.5 节第 6 条交接给新代理，沿用原 batch/task，新记 attempt。

### 11.3 任务包

填第 10 节「最小任务头」，并保证包含：工作区、阶段与角色、授权来源和最新批准输入版本、目标、允许读写的绝对路径、依赖、关联 B、当前设计/实现计数、编译/写回权限、**真实直接父代理（回执接收者）**、完成后的下一步和最终回执要求。

- Grok 任务：注明允许嵌套 Flash 的只读范围。
- Flash 任务：沿用原 batchId，记父 taskId、真实派发者标识和自己的 task/attempt；明确只读，写入/编译/写回权限均为无，不再派生。
- 主会话直接派的 Flash，父级是主会话；Grok 派的 Flash，父级才是 Grok。业务来源作者另记，不冒充实际父级。
- 只给必要上下文和规范路径，不复制整段聊天。任务头直接记入或引用到现有批次记录，不强制另存 JSON。

### 11.4 嵌套读取（主会话 → Grok → Flash）

- **分工**：主会话管整体分工、依赖、文件所有权和共享额度，可直接派多个任务共用的前置读取。Grok 执行中需要探索新文件、跨模块入口或依赖时，若其工具可派子代理，可直接派 Flash 并负责等待、续派和汇总，无须经主会话转派。单文件和修改点附近的小范围读取仍由 Grok 自己完成，不要求开工前读完所有潜在文件。
- **边界**：Flash 只读父任务已授权的范围；不改文件、不编译、不打包、不启动游戏、不写表、不作正式正确性或验收判断，也不再派生。父任务的写权限不会因复制上下文而授予 Flash。Grok 不另派 Grok 作者或 Astra；扩展分工或困难裁决交回主会话按额度安排。现有授权内的读取无需再问用户。
- **槽位**：整棵代理树共享实际可用槽位，父代理也计入；不写死集群规模，不循环探测空位。没有空位就先等已派任务，或由 Grok 做必要的局部读取。读取正在写入的范围前，先等写入收束或明确读取哪个版本。
- **事实包**：Flash 只向直接父代理交最终事实包：绝对路径与行号、相关符号/调用关系或原文事实、已读和未读范围、不确定项；会变的输入注明版本、哈希或读取时间。不倾倒全文。报告截断时向同一 Flash 补全（无续派工具则新派并说明），文件变化只补读受影响范围。
- **使用**：父代理等最终事实包后合并去重，再推进依赖它的工作。摘要不代替修改点原文：Grok 仍自行核对实际修改点的当前源码，写回者仍按第 8 节重读工作簿基线。事实中出现架构或正确性未决点，交主会话裁决，不让 Flash 批准设计。
- **收束**：Grok 交付前确认下属 Flash 全部返回且已 `close_agent`（或已通过受支持工具终止并确认终态），列出其真实标识、读取范围、采用的关键事实和未解决项；必需事实缺失就报告阻塞。主会话正常只收 Grok 汇总，异常、接管或必要协调时才展开下属。父任务中断不代表下属已停，恢复或换作者前先对账整棵相关子树。

### 11.5 等待、接收与续行

派发者负责把「子任务结束」接成下一步工作。自动完成事件、显式消息、最终回执和父代理实际处理是不同事实，不假定某条消息一定能唤醒已经结束回合的父代理。

1. **派发前**：每条写路径有唯一作者，前置任务已有完成回执，阶段额度已核对；共享注册器、资源库索引和制作表各由一个作者处理；无依赖、无写入冲突的工作按实际槽位并行。记下每个子代理的真实标识、直接父代理、batch/task/attempt、预期回执和完成后的下一步。
2. **等待**：有独立工作就先做，没有就用原生等待工具做有界等待。单次超时或空结果只表示这次等待结束；只要本轮仍有已授权的必要任务在运行，就继续下一次等待，不能因等了几轮或几分钟就发「先不空等」「结果回来再说」的 final。等待超时或用户停止等待，都不代表代理或其写入子进程已经停止。
3. **子代理回传**：完成、失败或遇到无法自行解除的阻塞时，若接口支持向父级发消息，就向已核实的直接父代理发一条短通知（task/attempt、状态、结果摘要或回执位置、写入与下属是否收束、待父方处理事项），再提交完整 final；不支持或发送失败就直接提交 final 并注明，不循环重发、不另开聊天、不换脚本。只保存文件不代替最终回复。正常完成不问「能否结束」，也不等父方确认才发 final，避免父子互等。
4. **接收与续行**：父代理取得完整 final 后，核对身份、输入、写入与下属收束，登记已接收，当轮推进已授权且依赖满足的下一步（汇总事实、额度内复核、返修、统一编译、写表或交付），不等用户再说「继续」。同一 task/attempt 的通知、完成事件和 final 只接收一次，不重复派发、不重复计轮次。额度耗尽时照样接收和整理，只是不再判断正确性。**登记后立即 `close_agent` 关闭该代理**：`multi_agent_v1` 的代理交完 final 不会自动结束，会一直占用全树共享槽位；关闭不影响以后用 `resume_agent` 按原标识续派。只有同一轮马上要向它续派时才暂缓关闭，续派完成后再关。
5. **缺通知或缺结果**：主动等待是主路径，消息只是补充。必要时用原生工具做一次最小状态对账；已确认终态却缺回执时，使用接口确有的结果获取能力，或向原代理一次性补要，不重跑实现。idle 不证明业务已完成。仍取不回就记录真实阻塞，不原地等待已结束的代理再次通知。
6. **返修与交接**：范围内返修和补充核对沿用原 batch/task，核对原代理标识、输入、回执、作者和写入状态后续派；仍在运行时不重复派同一写任务。原代理无法续用或需要调整分工时，先确认旧代理和相关写入已收束，再记录旧新标识、原因、已做/未做、输入版本和未决项，交给新代理并新记 attempt。不盲续「最近会话」，不借新代理重审已用完额度的阶段；仅停止等待不能释放文件所有权。
7. **逐级交付**：Flash → Grok → 主会话。Grok 接收 Flash 结果后继续本任务，不把每个事实包转给主会话调度，最终向主会话交汇总。
8. **结束与恢复**：只有完成、用户要求停止或暂停、确需用户决定、宿主强制结束或真实不可恢复阻塞时才结束本轮；如实交代未完成任务、真实代理标识、写入状态、回执位置和下一步，不承诺已结束的回合会在后台续行，也不用定时唤醒或脚本监控掩盖提前结束。恢复时先对账原代理和已有最终结果再接着做，不重开作者、不重做已完成工作、不清零额度。

来源案例：[设计五行属性原胚获取方式](codex://threads/01a1c131-790b-7c63-be85-fd58f027e572)中，父会话于 2026-11-10 01:20:36 以「先不再空等」结束，Grok 01:24:49 才提交最终复审报告，无人接续处理。因此关键在约束父方等待与续行，仅要求子代理多发消息并不足够。

### 11.6 最终回执与交付

批次记录至少保留：原生工具名与真实返回的代理标识、请求模型/推理档位与 Fast 配置依据、可观察返回身份、batch/task/attempt、输入版本、操作范围、最终回执位置、真实直接父代理及父方接收时间和下一步。后端或请求追踪信息未暴露就写未知，不为填字段另起 HTTP 客户端或抓取凭据。

执行者最终反馈须包含：改动文件和产物；完成与未完成事项；功能、美术、用户确认、正式接入的分别状态及占位待替换项；实际运行命令和适用的退出码；编译结果或「待统一编译/不适用」；写入是否收束；下属 Flash 的标识、读取范围、最终状态与未决项（没有则写不适用，不为填回执补开代理）；审批、失败与阻塞；下一步。身份与输入必须能对上本次任务。**成功创建代理、代理已结束、模型自报完成、正式复审通过、制作表已迁页是不同事实**；一句文本返回不能替代代码、编译或写表证据。

相关源码写入全部收束后，由指定执行子代理串行运行 `.\gradlew.bat compileJava --offline --no-daemon`。编译后仍按第 8 节核对正式美术、同版本用户确认和确认版接入，并取得独立写表回执；缺任何条件就留在制作中。

### 11.7 失败处理与旧渠道

- 429、TLS、未知模型、任务封装/协议错误、取消、审批拒绝或缺结果分别如实记录。429 本身不证明额度耗尽或套餐原因。遵循服务已配置的重试和回退，不在调度层循环换模型、账户或脚本探测，不通过换提供方、会话或放宽权限绕过审批。
- `task was sealed` / Multi-agent V2 封装：属于第 11.2 节的协议不匹配，不是模型不可用，也不是「窗口没刷新」。不据此判定 Grok、Flash 或原生集群不可用，也不把其他会话的成功或失败外推到所有会话。
- **美术 MCP 在上下文压缩后消失**：2026-11-12 观测到某会话 12:32 的工具清单含 `mcp__magpie`，14:08 压缩上下文后不再包含，重读技能也无法恢复。工具清单里根本没有 `mcp__magpie` 命名空间时，属于宿主没有提供工具，不是发现步骤遗漏：按美术技能做完有界检查后记为「当前会话工具未加载」，美术部分到新会话继续，或等待客户端修复。不改派 Grok 绘制建模，不用 headless 或其他实例冒充真实预览。
- 原生入口不能继续时，保留任务上下文和真实阻塞，独立且可推进的工作继续。不自动退回 Python/Shell/CLI 启动模型；主会话不接管 Java 或 Gradle。只有用户以后明确重新授权旧方案，才重新评估。
- 旧 `.grok/scripts/Invoke-CursorTask.ps1`、任务文件、Python 代理包装器和 `.grok/runs/` 执行证据保留历史，不修改、不删除、不再作为入口。项目正常业务脚本不属于废弃的启动渠道。回执不是第五张表，也不是唯一的需求或额度依据。
